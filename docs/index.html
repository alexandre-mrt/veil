The Problem

Every blockchain transaction is transparent by default. Amounts, senders, and receivers are permanently visible to anyone reading the chain. This creates a paradox: the technology that promises financial sovereignty also delivers total financial surveillance.

Existing privacy solutions force a binary choice:

Fully Anonymous
Tornado Cash, Zcash shielded pools — hide everything, creating regulatory risk and enabling illicit use.
Fully Transparent
Standard ERC-20 transfers, Sui token moves — provide no privacy at all. Every transaction is public.

There is nothing in between — no protocol that hides transaction amounts while still enforcing spending limits, allowing regulators to set thresholds without requiring identity disclosure below them.

The Solution

Veil introduces cumulative spending proofs — a novel ZK primitive:

  • Hides transaction amounts using Poseidon commitments bound to user identity
  • Enforces KYC-free spending limits (FINMA CHF 1,000/30 days) in zero-knowledge
  • Uses UTXO-style commitment consumption to prevent parallel chain attacks
  • Standardizes deposit denominations (100/500/1000 TOKEN) to resist amount correlation

How It Works

User: send 100 TOKEN privately | v [Browser — snarkjs WASM, ~2s] Compute Poseidon hashes (circomlibjs) Generate Groth16 proof (11 constraints) Prove: cumNew = cumOld + 100 cumNew <= threshold nullifier is unique commitments bound to userSecret | v [Sui Move — veil::pool] Verify proof: sui::groth16 BN254 native Consume old commitment (UTXO-style) Check nullifier not already spent Store nullifier + create new commitment Emit TransferEvent (no amounts, no identity)

ZK Circuit

The transfer circuit (transfer.circom) has 11 constraints and compiles to 3,211 R1CS constraints. It uses BN254 Groth16, verified natively on Sui via sui::groth16.

Epoch Design

Timeline: |-------------------------------------------- | Epoch 0 | Epoch 1 | Epoch 2 | [0, 30 days) | [30, 60 days) | [60, 90 days) | | Genesis: Poseidon(1, 0, 0, userSecret) | | | Epoch boundary: | | - New genesis commitment | | - cumulativeOld reset to 0 | | - randomness reset to 0 | | - New nullifier (different randOld) | | epoch_id = Clock::timestamp_ms() / 2,592,000,000

UTXO Commitment Model

Each shielded transfer is an atomic state transition. The old commitment is consumed (removed from dynamic fields), the nullifier is stored permanently, and a new commitment is created. This prevents parallel chain attacks where a user could fork from any historical commitment.

1. Consume
Old commitment removed via dynamic_field::remove. Must exist or abort.
2. Nullify
Nullifier stored permanently via dynamic_field::add. Must not exist or abort.
3. Create
New commitment added via dynamic_field::add. Must not exist or abort.

Privacy Red Team Report

An adversarial privacy analysis identified 15 findings. Verdict: The ZK circuit is cryptographically sound, but the protocol provides confidential transactions (amounts hidden) rather than private transactions (sender hidden). Achieving full sender privacy requires architectural changes (relayer, Merkle tree).

Findings

PRIV-001 Critical Cross-Epoch Identity Linking via Same Address
The same address calls deposit_and_register across epochs, trivially linking user identity. Fix: relayer pattern (Tier 2).
PRIV-002 Critical Sender Visible in Sui Transaction Metadata
shielded_transfer is signed by user's keypair. Sender address recorded in immutable tx metadata. Fix: relayer submits PTBs on behalf of users.
PRIV-003 Critical userSecret Plaintext in localStorage
XSS extracts userSecret from localStorage["veil-state"], enabling retroactive deanonymization of all past transactions. Fix: PBKDF2 + AES-GCM encryption (Tier 1).
PRIV-004 Fixed Deposit Amount Visible On-Chain
Fixed with standard deposit denominations (100/500/1000 TOKEN). Unique deposit amounts can no longer be used for correlation.
PRIV-005 High UTXO Chain Traceable via Dynamic Field Changes
Sui transaction effects reveal which CommitmentKey was removed/added, exposing the full commitment chain. Fix: Merkle tree accumulator (Tier 2).
PRIV-006 High Gas Coin Fingerprinting
Gas coin provenance creates unique fingerprints. Fix: sponsored transactions via relayer (Tier 2).
PRIV-007 High PTB Atomic Deposit + Transfer Link
A single PTB can call deposit_and_register then shielded_transfer atomically, proving the depositor is the transferor. Fix: commitment maturity period (Tier 1).
PRIV-008 Medium Anonymity Set Likely = 1
In low-usage periods, all transfers belong to the same user. Fix: display anonymity set size in UI, add deposit incentives.
PRIV-009 Medium txHistory Plaintext in localStorage
Transaction history stored as cleartext maps tx digests to amounts. Fix: encrypt or use commitment hashes (Tier 1).
PRIV-010 Medium Timing Correlation Deposit to Transfer
Immediate deposit-to-transfer pattern is a deanonymization signal. Fix: commitment maturity + UI guidance (Tier 1).
PRIV-011 Medium Admin-Gated Withdrawal (Censorship Risk)
Users cannot self-withdraw; admin learns identity + amount. Fix: ZK-proven withdrawal circuit (Tier 2).
PRIV-012 Low Proof Generation Time Side Channel
Practical impact low (fixed-size circuit). Accepted.
PRIV-013 Low Mock Proof Mode Zero Privacy
Dev-only fallback. Accepted.
PRIV-014 Info IP Leakage via RPC
Standard metadata leakage. Mitigate with Tor/VPN.
PRIV-015 Info txAmountHash Future Correlation
If salt leaks, amounts brute-forceable. Salt required per transaction.

Complete Deanonymization Attack Chain

PRIV-002 + PRIV-005 + PRIV-004 = Full Deanonymization
  1. Query all deposit_and_register txs → (address, deposit_amount, genesis_commitment)
  2. Query all shielded_transfer txs → (address, nullifier, old_commitment, new_commitment)
  3. Address in step 2 links directly to step 1 (same wallet)
  4. Commitment chain traces genesis → current via dynamic field changes
  5. Result: Complete tx graph with sender identity, amounts, ordering, epoch activity

Future Improvements

Tier 1 Quick Wins 1-2 days each
1.1 Encrypted Client-Side Storage
Fixes: PRIV-003, PRIV-009
PBKDF2 key derivation (600K iterations) + AES-GCM-256 encryption of userSecret and transaction history. Password prompt on load. Store commitment hashes instead of plaintext amounts.
1.2 Commitment Maturity Period
Fixes: PRIV-007, PRIV-010
Change CommitmentKey value from bool to u64 (creation epoch). Assert current_epoch > created_epoch before consuming. Prevents atomic deposit+transfer in one PTB.
Tier 2 Architecture Changes 1-2 weeks each
2.1 Relayer Pattern
Fixes: PRIV-001, PRIV-002, PRIV-006
Relayer submits PTBs on behalf of users. Users send proof data off-chain. The ZK proof authenticates the user (commitment bound to userSecret) — relayer cannot forge proofs or steal funds.
2.2 ZK-Proven Withdrawal
Fixes: PRIV-011
New withdraw.circom circuit. Users prove commitment ownership and withdraw without admin involvement. Nullifier with domain tag 4 prevents double-withdraw.
2.3 Merkle Tree Accumulator
Fixes: PRIV-005, PRIV-008
Replace individual dynamic fields with Poseidon Merkle tree (20 levels, ~7,200 additional constraints). On-chain only root changes; specific consumed commitments hidden. Anonymity set = all commitments ever.
Tier 3 Full Privacy Protocol 1-2 months
3.1 KYC Compliance Circuit
When cumulative spending exceeds threshold, user provides a second proof proving membership in a KYC credential Merkle tree. Identity still hidden — only "I have a valid KYC credential" is proved.
3.2 ElGamal Auditor Pattern
Each transfer includes an ElGamal encryption of (amount, randomness) under an auditor public key. Auditor can decrypt if legally required. Observers see only ciphertext. Selective disclosure without mass surveillance.
