# 2026-07-21 — BASELINE: measuring Veil end-to-end on one machine, once

## Status

This is the bootstrap night of the nightly research loop. `docs/research/` — `LEDGER.md`,
`EXPERIMENTS.md`, `NIGHTLY_PROMPT.md`, and this report format — did not exist before tonight. The
stored prompt referenced a `docs/research/2026-07-14-contra-confidential-transfers.md` worked
example and an existing ranked queue; neither existed anywhere in this repository's git history
(verified with `git log --all --diff-filter=A --name-only`). Rather than block on a

## Hypothesis

Veil's own circuit constraint counts, proving time, proof/VK/proving-key size, and browser proving
latency have never been measured together, on one machine, in one run — every number currently in
`README.md` was accumulated incrementally across unrelated commits, and gas cost per entry point has
never been measured at all. Establishing all of them in a single reproducible run, backed by a script
in `scripts/bench/`, is a falsifiable precondition: after this run, every future experiment in this
loop that claims "N% faster" or "N% smaller" has a number to diff against instead of re-deriving its
own ad hoc baseline.

## Threat / privacy model

This is a measurement experiment, not a cryptographic change — no new adversary is introduced and no
constraint is added, removed, or altered in any circuit. The threat-model relevance is indirect, through
two STRIDE categories already tracked in `docs/threat-model.md`:

- **Denial of Service (D2, D3):** gas cost per entry point bounds the cost of spamming the pool with
  transfers or dynamic-field growth. Tonight that number is UNMEASURED (see Results) — which is itself
  the finding: today nobody knows the actual cost of a griefing attempt in APT/gas units, only that a
  minimum-deposit floor exists in TOKEN terms (D3's stated mitigation). That gap should close before
  D2/D3's "Mitigated" status is fully trusted for gas-based griefing specifically.
- **Information Disclosure (I-adjacent, PRIV-012 in `docs/privacy-red-team-report.md`):** proof
  generation time as a side channel. PRIV-012 already argues practical impact is low because the
  circuit is fixed-size (same constraints regardless of the secret amount). Tonight's repeated proving
  measurements are consistent with that: variance across iterations (see Results) tracks system noise,
  not input values — all iterations use the same fixed witness, so this run cannot by itself rule out
  input-dependent timing, but it does confirm the constraint graph itself gives no structural reason for
  one to exist (no data-dependent branching in R1CS; every gate executes regardless of witness values).

**What this does NOT defend against, or establish:** this experiment says nothing about sender
anonymity (PRIV-002, still the protocol's core known gap), nothing about the single-contributor trusted
setup (still a pre-mainnet blocker per `README.md`), and nothing about Sybil resistance (E6). A
benchmark is not a mitigation.

**Assumptions:** BN254 pairing hardness for Groth16 soundness (unchanged — no proof-system work
happened tonight); the dev trusted setup produced tonight (`circuits/scripts/compile.sh`,
single contributor, `circuits/build/*_final.zkey`) is for benchmarking only and is not connected to
any deployed pool — it is not, and must never be treated as, a production key.

## Approach

Rebuilt the full circuit → proof pipeline from scratch on this container, independent of anything
already checked into the repo, and measured every stage instead of trusting the numbers already in
`README.md`:

1. Built `circom` 2.2.3 from source (`cargo build --release`, cloned from `iden3/circom`) — not
   preinstalled in this environment.
2. Compiled all three circuits (`transfer.circom`, `compliance.circom`, `withdraw.circom`) and read
   real R1CS constraint counts via `snarkjs r1cs info`.
3. Ran a dev Groth16 trusted setup (single contributor, matching `circuits/scripts/compile.sh`'s own
   caveat) for all three circuits against the same `pot15` Powers-of-Tau file the repo already
   references, and exported verification keys.
4. Wrote `scripts/bench/circuit-bench.mjs` — builds a valid witness for each circuit (same shape as
   `circuits/test/*.test.mjs`'s fixtures), runs `groth16.fullProve` + `groth16.verify` for N
   iterations natively in Node, and reports median proving/verification time plus proof/VK/zkey/wasm
   byte sizes.
5. Wrote `scripts/bench/browser-bench.mjs` + `scripts/bench/browser-harness/` — stages the compiled
   `transfer.circom` wasm/zkey next to a minimal HTML page that loads the same `snarkjs` UMD bundle
   the frontend ships, serves it over a local HTTP server (WASM needs to be fetched, not loaded from
   `file://`), and drives it with a real headless Chromium via Playwright. This measures the number a
   user's browser actually experiences, not a Node.js proxy for it.
6. Attempted to measure on-chain gas per entry point (`deposit_and_register`, `shielded_transfer`,
   `compliant_transfer`, `zk_withdraw`) via `sui move test` gas metering. **Blocked** — see Results.
7. Ran every test suite this session's tools could reach, for real, before writing any conclusion.

### Alternatives rejected

- **Estimating gas from Move bytecode/opcode counts instead of running `sui move test`.** Rejected:
  the whole point of tonight's rule is "no estimates presented as measurements." An opcode-count
  estimate would need its own calibration against real gas metering to be trustworthy, which is
  exactly the missing ingredient. Better to mark it BLOCKED/UNMEASURED honestly than publish a number
  that looks measured but isn't.
- **Using `circuits/test/*.test.mjs` directly as the benchmark** instead of a new `scripts/bench/`
  script. Rejected: those files assert pass/fail per constraint case (correctness), not timing: they
  are not written to isolate and report proving latency, and folding a benchmark into them would
  couple a reusable perf tool to the correctness-test file layout. A dedicated script matches the
  prompt's explicit requirement ("Benchmarks go in a reusable script under scripts/bench/").
- **Timing the browser number by running the actual Next.js app** in a real browser session (wallet
  connect, full `useProofGeneration` hook) instead of a minimal harness page. Rejected for tonight:
  the full app needs a funded testnet wallet and a live RPC round-trip unrelated to proving time
  itself, which would conflate network latency with WASM proving latency. The harness loads the exact
  same `snarkjs` bundle and wasm/zkey artifacts the app serves from `frontend/public/circuits/`, so it
  isolates the number this experiment is about. A full end-to-end browser latency number (including
  wallet + RPC) is a reasonable separate follow-up.

### Proving time, verification time, artifact sizes — server-side (Node, native)

Reproduce: `cd scripts && node bench/circuit-bench.mjs --iterations 7`

| Circuit | Prove (median, 7 iters) | Verify (median) | Proof size | VK size | zkey size | wasm size |
|---|---|---|---|---|---|---|
| `transfer.circom` | 759.8 ms | 26.6 ms | 723 B | 4,025 B | 6,001,431 B (5.7 MB) | 2,846,127 B (2.7 MB) |
| `compliance.circom` | 715.3 ms | 24.9 ms | 721 B | 3,838 B | 5,682,157 B (5.4 MB) | 2,931,887 B (2.8 MB) |
| `withdraw.circom` | 237.4 ms | 23.7 ms | 724 B | 3,656 B | 1,385,335 B (1.3 MB) | 2,346,258 B (2.2 MB) |

Raw per-iteration data (ms), `transfer.circom`: `1147.1, 773.4, 759.8, 754.2, 762.3, 754.8, 743.8`
(first iteration includes one-time module/JIT warmup; the other six cluster tightly around 750-775 ms).
Full JSON for all three circuits, all iterations, is in the script's own stdout — see command above.

Constraint count vs. prove time roughly tracks linearly across the three circuits (13,611 → 760 ms,
12,743 → 715 ms, 3,058 → 237 ms), consistent with Groth16's proving cost scaling with circuit size
rather than public/private input count (`withdraw.circom` has far fewer inputs than the other two but
its constraint-to-time ratio is in the same ballpark: ~13.3k constraints/13.3k ms for transfer vs.
~12.9k constraints/~12.9k ms — actually closer to ~0.056 ms/constraint for transfer/compliance and
~0.078 ms/constraint for withdraw, i.e. withdraw is *less* efficient per-constraint, likely fixed
per-proof overhead (FFT setup, witness marshalling) amortizing worse over a smaller circuit).


Median 1,129.9 ms vs. 759.8 ms server-side (Node) — the browser is ~49% slower for the same circuit,
same wasm witness calculator, same snarkjs version. This is expected (V8's WASM path inside a
sandboxed renderer process vs. Node's native WASM runtime, plus this harness runs single-threaded, no
Web Worker parallelism, matching how `useProofGeneration.ts` actually invokes it) but had never been
measured before. The first iteration (2,187 ms) includes one-time WASM module compilation the frontend
would normally pay once per session, not per proof.

**Caveat, stated plainly:** this ran on the same container CPU as everything else tonight — a
server-class x86_64 core, not a phone. It is a real, current number for "desktop browser, no Web
Worker," not for "mobile." A mobile-class number (throttled CPU or an actual device) is queued as a
follow-up in `EXPERIMENTS.md` rather than invented here.

### On-chain gas per entry point — BLOCKED

**Not measured.** `sui` CLI is not installed in this environment and could not be installed tonight:

- No `sui` binary present, no `apt` package for it, and no cargo-published `sui` crate on
  crates.io (`cargo install circom` worked for the ZK compiler; the equivalent `cargo install sui`
  path does not exist for the Sui CLI).
- No prebuilt release binary reachable: `https://github.com/MystenLabs/sui/releases/...` returns a
  403 from this session's egress policy (GitHub access is scoped to `alexandre-mrt/veil` only for
  the API/web/release-asset paths; only the git smart-HTTP protocol — plain `git clone` — is
  reachable for other repositories).
- Building `sui` from source (`cargo build --release --bin sui -p sui`, cloned via `git clone
  --depth 1 https://github.com/MystenLabs/sui.git`) was attempted. The workspace is ~126 crates
  including full node/indexer/RPC infrastructure the CLI links against. The build failed during
  dependency resolution with a transient network error fetching a git dependency (`tabled`) through
  cargo's built-in git client (`failed to receive HTTP 200 response: got 502`) — cargo's internal
  git fetcher does not reliably traverse this session's proxy the way `git`/`curl` do. The
  documented fix (`net.git-fetch-with-cli = true` in a global `~/.cargo/config.toml`) requires
  editing configuration outside the repository, which this unattended session is not authorized to
  do without a live approval. The session's container also restarted once mid-build, independently
  losing that attempt's progress.

This is a real, exactly-stated blocker, not an estimate dressed up as one. **Fallback (UNMEASURED,
design-only):** reading `contracts/sources/pool.move`, the entry points do the following on-chain
work, which is the qualitative shape any future gas measurement should expect to see costed:

- `shielded_transfer`: 1 Groth16 verification (`sui::groth16`, transfer VK) + 1 dynamic-field
  `remove` (spent `oldCommitment`) + 2 dynamic-field `add` (new commitment, nullifier).
- `compliant_transfer` (in `compliance.move`, called when `compliance_required == true`): the above,
  plus a **second** Groth16 verification (compliance VK) + 1 more dynamic-field `add` (credential
  nullifier) + an ECDH/AES-GCM ciphertext written into `ComplianceVerifiedEvent`.
- `zk_withdraw`: 1 Groth16 verification (withdraw VK) + 1 dynamic-field `remove` + 2 dynamic-field
  `add` (new/change commitment, withdrawal nullifier).
- `deposit_and_register`: no Groth16 verification, 1 dynamic-field `add` (initial commitment).

Every entry point's dominant on-chain cost should be the Groth16 verification(s); `sui::groth16` gas
cost is protocol-defined and roughly constant per proof regardless of the circuit that produced it
(pairing check cost, not R1CS-size-dependent) — meaning `compliant_transfer` should cost close to 2×
a plain `shielded_transfer`'s verification gas, plus the marginal dynamic-field and event-emission
cost. This is a prediction to be confirmed, not a measurement, and is written here as UNMEASURED.

**Second incidental finding, fixed in this PR:** `.gitignore` ignored `build/` (matching

one line each, no other change.

Circuit constraints, proving/verification time, proof/VK/zkey/wasm sizes, and browser proving latency

On-chain gas per entry point is explicitly BLOCKED, documented above with the exact reason, and carried

## Where this could be used

- **Any Circom + Groth16 + snarkjs project shipping browser-side proving** — the
  `scripts/bench/browser-bench.mjs` pattern (stage the same wasm/zkey/snarkjs bundle the app ships,
  serve over local HTTP, drive with headless Chromium via Playwright) is a reusable way to get a real
  in-browser proving number without standing up the whole app, wallet, and RPC stack. Directly
  applicable to any Sui/Ethereum dApp doing client-side ZK (private voting, confidential auctions,
  anonymous credentials).
- **Any protocol doing dual-proof compliance gating** (a "prove eligibility" proof plus a "prove
  compliance" proof verified atomically on-chain, as `compliant_transfer` does) — the qualitative
  gas shape here (2× Groth16 verification + extra dynamic-field writes) generalizes to confidential
  payroll with a compliance sidecar, or any KYC-gated DeFi primitive on a chain with native pairing
  precompiles.
- **A thesis chapter on "the cost of compliance-gated privacy"** — this baseline is the first data
  point for a comparison table (Groth16 dual-proof vs. a single aggregated proof vs. a non-ZK
  allowlist) that a thesis on regulated privacy protocols would want as its opening figure.
