# 2026-09-17 — Poseidon2 vs Poseidon: constraint attribution + a real Merkle-hash swap (queue item #2)

## Hypothesis

Swapping Veil's current hash primitive (circomlib's `Poseidon`, a sponge with a single absorb)
for Poseidon2 at the sites where an official Poseidon2 parameter set actually exists reduces
R1CS constraint count and Groth16 proving time — specifically for the depth-20 Merkle-membership
check in `transfer.circom`/`compliance.circom`, which the constraint-attribution measurement below
shows accounts for 75-80% of each circuit's non-linear constraints. This experiment also settles
the queue's second framing of the same question directly: the exact non-linear-constraint
contribution of every Poseidon instance in all three circuits, fully reconciled against the
2026-07-22 baseline totals.

## Threat / privacy model

**What this experiment could change, if merged:** the collision-resistance / preimage-resistance
assumption backing the depth-20 commitment-tree node hash inside `transfer.circom` and
`compliance.circom` (`templates/merkle_proof.circom`'s `MerkleProof(20)`), and, transitively, the
soundness of "old commitment is a member of the anonymity set" (C0 in both circuits). Nothing about
the commitment/nullifier/credential hash sites (`Poseidon(4)`, `Poseidon(5)`) changes — see Results,
they are architecturally out of scope for this swap.

**Adversary model, unchanged from `docs/threat-model.md`:**
- **Chain observer** — sees Merkle-root updates and (for withdrawals) which commitment was spent,
  never which leaf a transfer's `oldCommitment` corresponds to. This experiment does not change what
  a chain observer learns: the public interface (`merkleRoot`, `oldCommitment` stays private) is
  identical before and after the swap. Maps to `docs/threat-model.md` RR5 (deposit-commitment
  linkability) — the swap does not change the anonymity-set size (still bounded by depth 20 = 2^20
  leaves), only the cost of proving membership in it.
- **Malicious prover** — must not be able to produce a valid `TransferPoseidon2` proof for a
  `merkleRoot` without actually knowing an authentication path to a leaf that hashes to it under
  `MerkleProof2`'s node function. This is exactly what `merkleRoot === membershipProof.root` (a hard
  R1CS equality, not an assertion outside the constraint system) enforces, and what N1-N3 in
  `circuits/test/transfer_poseidon2.test.mjs` test adversarially (forged sibling, flipped path bit,
  substituted leaf — see Approach).
- **What this does NOT defend against, unchanged:** sender identity is still visible (`PRIV-002`,
  unrelated to hashing), the trusted setup for whatever zkey a deployment uses is still a
  single-dev-contributor ceremony (RR2 — this experiment's own zkey is exactly that, see Approach),
  and swapping the Merkle hash does nothing for the arity-4/5 identity-bound hash sites this
  experiment could not touch (see Results — that's the more interesting finding here, arguably).

**Soundness argument for the swap itself.** `MerkleProof2` replaces circomlib's
`Poseidon(2)` (a sponge: state width t=3, one fixed-zero capacity element, 2 rate elements) with
Poseidon2 in 2-to-1 **compression mode** (state width t=2, no capacity element, output fed forward
with the first input: `out = Permutation([l,r])[0] + l`). This is not an invented construction —
it is exactly what `@taceo/circom-lib`'s own `binary_merkle_root.circom` uses for Merkle nodes (see
Approach for provenance), a standard Miyaguchi-Preneel-style feed-forward that gives one-wayness
from a public permutation. The permutation itself is the reference Poseidon2 (Grassi, Khovratovich,
Schofnegger, [eprint 2023/323](https://eprint.iacr.org/2023/323)) at BN254, with round constants
generated by the paper's own reference (HorizenLabs) parameter script — not re-derived or
hand-rolled in this session. Collision resistance of the compression function reduces to the
permutation's own security margin (128-bit, same target as circomlib's Poseidon), which is a
property of the published parameters, not of how this experiment wires them into a Merkle tree.

One caveat carried over unchanged, not introduced by this swap: neither the original
`merkle_proof.circom` nor `merkle_proof_poseidon2.circom` domain-separates *between tree levels* —
a leaf value could in principle be crafted to look like an internal node's hash at a shallower
depth. `@taceo/circom-lib`'s own docstring calls this out explicitly for exactly this reason. This
is an existing property of Veil's Merkle design (both before and after this experiment), not a
regression; worth its own line in `EXPERIMENTS.md` (see Open questions) since two circuits now share
the shape.

**Assumptions:** BN254 discrete-log hardness (Groth16, unchanged), Poseidon2's own security margin
at t=2/t=3/t=4 per the published parameters (no assumption made about t=5/t=6 — see Results, those
states have no official parameters and are untouched here), and — same caveat as every zkey in this
repo including the 2026-07-22 baseline's — this experiment's own trusted setup is a fresh,
single-dev-contributor local ceremony, not production-safe (RR2).

## Approach

**What I built:**

1. `circuits/bench-circuits/` — nine standalone single-primitive circuits, each instantiating
   exactly one hash call with no surrounding logic, isolating that primitive's raw R1CS cost:
   circomlib `Poseidon(2..5)` (arities used across all three real circuits), Poseidon2 in sponge
   mode at t=3/t=4 (matching circomlib's own sponge convention, for a first naive comparison), and
   Poseidon2 in 2-to-1 compression mode at t=2 (the construction actually worth using for a
   Merkle node — see Results for why the first comparison was misleading). Plus seven gadget
   circuits (`Num2Bits(64/8)`, `GreaterThan(64)`, `LessEqThan(64)`, `GreaterEqThan(64/8)`,
   `MultiMux1(2)`) to close out the full non-Poseidon share of each real circuit's constraints.
2. `scripts/bench/poseidon-arity-compile.sh` + `poseidon-arity-latency.mjs` — reusable, **fully
   offline** benchmark: compiles all bench circuits, generates a fresh local Powers of Tau (bn128,
   2^12, single dev contribution via `snarkjs powersoftau`) rather than downloading a third-party
   ptau (network access to `storage.googleapis.com`/Hermez's S3 bucket was blocked this session —
   see the on-chain-gas blocker below for the general pattern), runs Groth16 setup per circuit, and
   times `snarkjs.groth16.fullProve` (20 runs/circuit, `process.hrtime.bigint()`).
3. `circuits/templates/merkle_proof_poseidon2.circom` (`MerkleProof2`) + `circuits/transfer_poseidon2.circom`
   — a research variant of `transfer.circom`, byte-for-byte identical except C0 (Merkle membership),
   which uses `MerkleProof2` (Poseidon2 compression) instead of `MerkleProof` (circomlib Poseidon
   sponge). Everything else — C1-C11, domain tags, range checks — is unchanged.
4. `circuits/test/transfer_poseidon2.test.mjs` — 2 happy-path tests (genesis position, and a
   non-trivial mixed-sibling path) and 3 adversarial tests: **N1** forged sibling, **N2** flipped
   `pathIndices` bit, **N3** a substituted leaf claiming membership under the original root. All
   three must make `snarkjs.groth16.fullProve` throw (the witness cannot satisfy
   `merkleRoot === membershipProof.root`), not just fail a JS-side check.

**Where the Poseidon2 implementation came from.** `@taceo/circom-lib` (npm, MIT license,
[`TaceoLabs/taceo-circom-lib`](https://github.com/TaceoLabs/taceo-circom-lib)) — its own README
states the Poseidon2/EdDSA-Poseidon2/BabyJubJub circuits are "pulled from the audited repository
for TACEO:OPRF" (`TaceoLabs/oprf-circom`). I used its published round constants and matrix
constructions as-is; I did not generate or modify any cryptographic parameter in this session. Its
companion JS package `@taceo/poseidon2` (parity-tested against a Rust reference implementation, per
its own README) was used for computing test witnesses.

**What I rejected.** First attempt: comparing circomlib `Poseidon(2)` against Poseidon2 in **sponge**
mode (t=3, matching circomlib's own state-width convention) — see Results, this was the wrong
comparison (more constraints, not fewer) and I initially almost reported it as the headline number.
Re-reading `@taceo/circom-lib`'s own `binary_merkle_root.circom` showed it deliberately uses
**compression** mode (t=2) for Merkle nodes specifically because it avoids the sponge's extra
capacity element — re-ran with that construction and got the opposite, correct-shaped result. Kept
both numbers in the Results table below since the gap between them is itself the finding: **don't
swap a permutation in naively — use the construction mode the reference implementation recommends
for the use case**, and blind "same primitive, same call shape" substitution can make things worse.

I also rejected inventing Poseidon2 parameters for the t=5/t=6 states Veil's identity-bound
commitment hash (`Poseidon(4)`) and credential-leaf hash (`Poseidon(5)`) would need for a *full*
migration — `@taceo/circom-lib` only ships audited parameters for t ∈ {2,3,4,8,12,16} (this matches
the reference Poseidon2 paper's own published parameter sets, not an implementation gap specific to
this one library). Deriving new round constants for t=5/t=6 is exactly the kind of self-rolled
cryptography this loop's rules forbid ("no estimates presented as measurements," and by extension no
home-grown parameters presented as audited ones). This is a real architectural blocker for a
whole-protocol migration, not a corner I cut — see Results and Where this could be used.

**Important caveat on the standalone timings**, stated up front so the number isn't over-read: all
seven bench circuits are under 900 constraints, i.e. all land in the *same* Groth16 FFT domain
(next-power-of-2 = 1,024). The sponge-mode Poseidon2 circuits prove *faster* than circomlib
Poseidon here (e.g. `poseidon2_t3` at 88.47ms vs `poseidon_t2` at 108.99ms) **despite having more
R1CS constraints** — because at this size, proving wall-clock is dominated by fixed per-call
overhead (WASM witness-calculator instantiation, zkey read) and by the WASM witness-generation
program's actual instruction count, not by the FFT/MSM cost that scales with constraint count. This
does **not** mean "Poseidon2 sponge mode is free" — it means a micro-benchmark this small can't
distinguish "more constraints" from "same asymptotic domain, faster witness code." The
whole-circuit measurement below (13k+ constraints, where domain-size effects are what's actually
relevant to Veil) is the one that should be trusted for a real verdict; the compression-mode number
(-11% non-linear, -18% zkey, -32% proving time, all pointing the same direction) is the one where
standalone and full-circuit results agree.

## Verdict: **KEEP** (research artifacts + a real, positive, reproducible finding — not a production migration)

Every number in Results came from a command actually run this session, including the one the
hypothesis named (proving time). The Merkle-only Poseidon2-compression swap is real: **-4.9% total
constraints, -4.3% zkey size, -5.9% proving time**, using an audited third-party implementation's own
recommended construction, with three passing adversarial soundness tests. That's worth keeping as a
citable, reproducible result and as working code — `transfer_poseidon2.circom`, its test suite, and
the four benchmark scripts under `scripts/bench/` are merged with this PR.

**What KEEP does *not* mean here:** this is not a proposal to replace `transfer.circom` in
production, and this PR does not touch `BASELINE.md`'s protocol-state numbers or `compliance.circom`
(which has the same Merkle structure and would benefit identically, but doubling the diff doesn't
change the finding). Three reasons:

1. **The swap is architecturally partial.** Poseidon2 has no official parameter set for the t=5/t=6
   states the identity-bound commitment hash (`Poseidon(4)`, 6 instances) and the credential-leaf
   hash (`Poseidon(5)`, 1 instance) need. A real migration can only ever touch the Merkle sites
   (41 of 51 total Poseidon calls across the protocol) — meaningful, but not "Veil moved to
   Poseidon2," just "Veil's Merkle tree did."
2. **Adoption cost is real and this PR doesn't pay it.** Swapping the production circuit means a new
   verifying key, which means the timelocked on-chain VK-update path (`docs/threat-model.md`'s
   existing 1-epoch VK timelock machinery, built for exactly this) must actually run, a production
   (multi-contributor) ceremony must replace the dev-only local one this experiment used, and
   `frontend/src/hooks/useProofGeneration.ts` plus the relayer's proving path need the new
   wasm/zkey. That is deployment engineering, not a research-night diff.
3. **One hypothesis per night.** Applying the same swap to `compliance.circom` (identical Merkle
   structure, same expected ~5% win) is a five-minute change but a second circuit's worth of
   re-verification (its own negative tests, its own A/B) — real work, correctly out of scope tonight.

## Where this could be used

- **Any Circom/Groth16 protocol with a Poseidon-sponge Merkle accumulator** — the 75-80% non-linear-
  constraint share measured here is not Veil-specific; any depth-N Merkle-membership circuit built
  the "obvious" way (circomlib `Poseidon(2)` per level) is paying a sponge's capacity-element tax N
  times for no benefit, since a Merkle node hash never needs more than one output element. Swapping
  to a compression-mode 2-to-1 hash (Poseidon2 or otherwise) is close to a free 5-10% win for that
  entire protocol class — mixers, nullifier-set trees, any UTXO-shielded-pool design.
- **A thesis chapter on hash-primitive selection for SNARK circuits** — the sponge-vs-compression
  naive-swap result (Results table: +12% to +41% constraints for the "obviously equivalent" sponge
  substitution) is a better cautionary example than a clean win would have been: "using the newer
  primitive" and "using it correctly" are different questions, and benchmarking the wrong
  construction mode would have produced a confidently wrong REJECT.
- **Any protocol maintaining parallel Merkle-tree circuits for different note types** (Veil's own
  `compliance.circom` credential tree is the immediate next candidate) — the win compounds per tree
  without touching the harder-to-migrate identity/credential hash sites.
