# 2026-08-13 — Poseidon2 vs Poseidon for Veil's hash instances (queue item #2)

## Hypothesis

Swapping circomlib's Poseidon for TACEO's audited Poseidon2 implementation
(`@taceo/circom-lib`, BN254, state sizes t ∈ {2, 3, 4, 8, 12, 16}) reduces R1CS
constraint count and Groth16 proving time for **at least one** class of hash
instance Veil actually uses today, measured on real compiled circuits, not
estimated from the Poseidon2 paper's asymptotic claims. Veil uses Poseidon at
four distinct arities across `transfer.circom`, `compliance.circom`, and
`withdraw.circom` (2-input Merkle-level hash ×20 per membership proof,
domain-tagged 2/3/4-real-input commitment, nullifier, and credential-leaf
hashes); this experiment measures the delta at every arity actually in use,
not just the one the literature is easiest to cite for.

Before tonight: zero of Veil's Poseidon call sites had a measured Poseidon2
comparison. This experiment moves that to five (one per arity in use, plus
the full 20-level Merkle proof end to end), each with a real compiled circuit,
a real R1CS constraint count, and — for the highest-value case — a real
Groth16 proving-time delta.

## Threat / privacy model

No production circuit, Move module, or frontend code changed in this PR — see
Verdict. The relevant adversary framing here is about who acts on these
numbers, not about a new attack surface:

- **This research loop, on future nights.** A wrong or optimistic constraint
  delta would misdirect the next queued experiment (batched proofs, Merkle
  scaling) into optimizing the wrong thing.
- **A future engineer deciding whether to port Veil's circuits to
  Poseidon2**, who needs an honest answer including the cases where it's a
  *loss*, not just the case where it wins — this report exists specifically
  because the queue's framing ("Poseidon2 reduces constraints") turned out
  to be true for one arity and false for two others, and only measuring all
  of them surfaces that.

**What adopting Poseidon2 (if it happened) would and would not change,**
since this is worth stating precisely even though nothing was adopted
tonight: Poseidon2 is believed to satisfy the same security properties as
Poseidon over BN254 — it targets the same field, the same algebraic
attack surface (Gröbner basis / interpolation attacks the wide/narrow round
counts defend against), and is specified in a peer-reviewed paper
(eprint.iacr.org/2023/323) with parameters this vendored library says are
generated by the same HorizenLabs script used for other production Poseidon2
deployments. Swapping the *hash function* does not touch Groth16 soundness
(`docs/threat-model.md` RR1, BN254 discrete-log — unaffected), the trusted
setup (RR2 — a new circuit still needs a new ceremony, see Verdict), or
sender/recipient anonymity (`README.md`'s honest "no" on both — a hash
function change doesn't touch who signs the transaction). It also does not,
by itself, change nullifier-collision or domain-separation soundness — see
Approach for what actually would need re-arguing if this were adopted for
real, and Open Questions for what's unverified.

**What this experiment itself does not defend against or establish:** it is
not a cryptanalysis of Poseidon2 (I did not re-derive round-constant
generation or check for known attacks beyond trusting the cited paper and
the vendor's own test-vector parity claim with their Rust implementation);
it is not a statement that this specific library is production-ready for
Veil (see Open Questions); and the domain-separation scheme evaluated for
the "adopt Poseidon2's own idiom" comparisons (tag folded into the sponge's
capacity element, via `Poseidon2Sponge(N, T, DS)`) is a **different**
domain-separation construction from Veil's current one (tag as the first
rate element) — swapping to it would change which bits of the circuit
protect against nullifier/commitment cross-domain collisions, and that
change has not been independently audited here beyond the reasoning in
Approach.

Assumptions carried over unchanged: Groth16/BN254 soundness, the existing
dev-only trusted setup's toxic waste not being production-safe (RR2, still
open, still unrelated to this experiment).

## Approach

**What I built.** `scripts/bench/poseidon-compare/` — nine standalone Circom
circuits plus two benchmark/test scripts, all self-contained (no production
circuit was included or modified):

- `circuits/p1_t3.circom` … `p1_t6.circom` — one circomlib `Poseidon(n)` call
  each, wired to match production usage exactly at every arity Veil uses:
  `p1_t3` (2 signal inputs, no tag — `templates/merkle_proof.circom`'s
  per-level hasher), `p1_t4` (1 constant tag + 2 signals —
  `transfer.circom`'s `txAmountHash`, `compliance.circom`'s `nfHash`/
  `ctxHash`), `p1_t5` (1 tag + 3 signals — `transfer.circom`'s
  `oldHash`/`newHash`/`nfHash`, `withdraw.circom`'s `commHash`/`changeHash`/
  `nfHash`), `p1_t6` (1 tag + 4 signals — `compliance.circom`'s `leafHash`).
- `circuits/p2_merkle_t2_compress.circom`, `p2_t3_sponge.circom`,
  `p2_t4_sponge.circom`, `p2_t8_sponge.circom` — the Poseidon2 equivalents,
  using two different constructions from the vendored library (see below).
- `circuits/p1_merkle20.circom` / `p2_merkle20.circom` — the full 20-level
  membership proof (Veil's actual Merkle depth, both `transfer.circom` and
  `compliance.circom`), structurally identical (same `MultiMux1` left/right
  selection, same fixed depth, same public root) with only the per-level
  hash primitive swapped, so the measured delta is attributable to the hash
  primitive alone and not to any change in proof structure.
- `vendor/poseidon2/` — `poseidon2.circom`, `poseidon2_constants.circom`,
  `compression.circom`, `precomputations.circom` copied verbatim (MIT
  license, `LICENSE-taceo` kept alongside) from `@taceo/circom-lib` v0.6.0
  (npm), whose `poseidon2.circom`/`compression.circom` are pulled from
  TACEO's audited `oprf-circom` repository per that package's README.
- `measure-constraints.sh` — recompiles every circuit here and prints
  `snarkjs r1cs info` for each; reproduces the constraint table below.
- `prove-latency.mjs` — same warm-up-then-N-timed-runs methodology as
  `scripts/bench/prove-latency.mjs`, applied to `p1_merkle20` vs
  `p2_merkle20` (the highest-instance-count, highest-value comparison).
- `negative-test.mjs` — confirms a real Groth16 verify against
  `p2_merkle20` accepts a valid proof and rejects one with a tampered public
  output, so the constraint-count and proving-time numbers below are not
  measuring a tautological circuit that would accept anything.
- `verify_t3.circom` (not part of the constraint measurements) — used once,
  ad hoc, to cross-check the vendored circuit's output against
  `@taceo/poseidon2`'s independent JS reference implementation for the same
  input; see Results.

**Two different Poseidon2 constructions, used deliberately for different
call sites — not a uniform find-and-replace:**

1. **Merkle-level hash → Poseidon2 "compression mode"** (`out = perm(t=2)(a,
   b)[0] + a`). This is not my invention — it's the exact construction
   TACEO's own `binary_merkle_root.circom` uses per tree level, chosen
   because a 2-to-1 compression function only needs a **t=2** permutation
   (Miyaguchi–Preneel-style), one state size smaller than a same-arity
   sponge (t=3) would need, and directly comparable in role (not raw hash
   value, but "compress two children into a parent") to what
   `templates/merkle_proof.circom` already does with `Poseidon(2)`.
2. **Domain-tagged hashes → `Poseidon2Sponge(N, T, DS)`**, folding the
   domain tag into the sponge's **capacity** element (`DS`, a compile-time
   constant) instead of consuming a rate slot as Veil's current Poseidon
   calls do (`inputs[0] <== <tag>`). This is the idiomatic Poseidon2 way to
   domain-separate and — critically — it means a hash with N "real" inputs
   only needs a permutation of size `T = N + 1` rounded up to a supported
   state size, not `T = N + 2` the way circomlib's tag-as-rate-element
   pattern requires. For N=2 (`txAmountHash`-class), T=3 exactly fits — no
   waste. For N=3 (`oldHash`/`newHash`/`nfHash`-class), T=4 exactly fits.
   For N=4 (`leafHash`), the next supported size above T=5 is **T=8** — the
   library doesn't ship t=5 or t=6, so this rounds up and wastes 3 rate
   slots. This mismatch is the central finding below, not an
   implementation bug to route around before reporting.

**What I rejected.** Hand-deriving Poseidon2 round constants and an MDS/
diagonal matrix for exact state sizes t=5 and t=6 (the sizes circomlib's
`Poseidon(4)` and `Poseidon(5)` actually use) so every arity would have a
same-size Poseidon2 comparison — rejected for tonight because generating
and self-verifying new round constants correctly (avoiding a broken or
weak permutation that happens to compile) is a multi-night cryptographic
task in its own right, not something to rush to get a cleaner table. Using
the vendor's supported sizes and reporting the real padding cost honestly
is the more defensible choice; the t=5/t=6 gap is now an explicit, ranked
open question instead of a silently-avoided one.

I also rejected modifying `transfer.circom`/`compliance.circom` in place
for this PR (building a `-poseidon2` variant of the production circuits,
regenerating a trusted setup, updating `verifier.move`'s VK) — that's a
real circuit change with its own soundness/leakage/negative-test
obligations and its own trusted-setup ceremony, appropriately a dedicated
future night's work once the numbers below say which parts are worth it.
Tonight's deliverable is the number, not the migration.

**Correctness check.** Constraint count is a purely structural property (it
doesn't depend on whether the wiring computes the intended function), so
none of the numbers below would change if `vendor/poseidon2/poseidon2.circom`
were subtly wrong. To make sure "Poseidon2" here means the real algorithm
and not a broken permutation that happens to compile, I cross-checked a raw
`Poseidon2(3)` permutation's output for input `[0, 1, 2]` against
`@taceo/poseidon2`'s independent JS/TypeScript implementation (same
publisher, explicitly "parity-tested against the Rust `taceo-poseidon2`
crate", `@noble/curves`-based, no shared code with the Circom template).
Both produced the identical field element for all three output limbs — see
Results.

## Results

### Constraint counts (raw `snarkjs r1cs info`, `CIRCOM=/tmp/circom/target/release/circom bash measure-constraints.sh`)

| Instance class | Poseidon1 (circomlib) | Poseidon2 (TACEO) | Δ constraints | Δ % |
|---|---|---|---|---|
| Merkle level, 2 signal in, no tag (t: 3→2) | **517** (243 NL / 274 lin) — `p1_t3` | **484** (216 NL / 268 lin) — `p2_merkle_t2_compress` | −33 | **−6.4%** |
| Full 20-level Merkle proof (Veil's actual depth) | **10,400** (4,920 NL / 5,480 lin) — `p1_merkle20` | **9,740** (4,380 NL / 5,360 lin) — `p2_merkle20` | −660 | **−6.35%** |
| `txAmountHash`-class, N=2 real + tag (t: 4→3) | **605** (264 NL / 341 lin) — `p1_t4` | **580** (240 NL / 340 lin) — `p2_t3_sponge` | −25 | **−4.1%** |
| commitment/nullifier-class, N=3 real + tag (t: 5→4) | **736** (300 NL / 436 lin) — `p1_t5` | **852** (264 NL / 588 lin) — `p2_t4_sponge` | **+116** | **+15.8%** |
| `leafHash`-class, N=4 real + tag (t: 6→8, padded) | **835** (324 NL / 511 lin) — `p1_t6` | **1,663** (363 NL / 1,300 lin) — `p2_t8_sponge` | **+828** | **+99.2%** |

Non-linear (multiplication-gate) count drops in **every** case — Poseidon2's
partial-round S-box placement is genuinely cheaper per permutation. But
**total R1CS constraints**, which is what determines the Groth16 proving-key
FFT domain size, only drops for the two cases where the permutation's state
size didn't need to round up (t=2 and t=3→ the exact-fit N=2 sponge). At
N=3→t=4 the external-matrix linear layer costs more low-degree constraints
than the non-linear savings recover; at N=4→t=8 padding three unused rate
slots makes it nearly double the cost of the circuit it replaces.

## Verdict: **PARK**

The measurement goal for tonight — does Poseidon2 move Veil's constraint
count, and by how much, for every arity actually in use — is fully answered,
with real numbers and a working, correctness-checked implementation for
each. The answer is genuinely mixed, and that's the finding: **the Merkle
accumulator (20 instances per proof, the single largest source of Poseidon
constraints in both `transfer.circom` and `compliance.circom`) is a clear
win at −6.35% per proof / −4.85% to −5.18% of the whole circuit; the
domain-tagged commitment/nullifier/credential hashes are a net loss with
this library's available state sizes**, because Veil's real arities (t=5,
t=6) fall in the gap between Poseidon2's supported sizes (…4, 8, 12, 16…)
and padding up to the next one costs more in linear constraints than the
non-linear savings recover.

**Parked, not shipped**, on:

1. Actually porting `templates/merkle_proof.circom` to Poseidon2 compression
   mode in the production circuits, which requires its own trusted-setup
   ceremony (new circuit ⇒ new proving/verifying key — RR2 applies fresh),
   an updated `verifier.move` VK (timelocked per `README.md`), a
   soundness re-argument for the compression construction specifically (see
   Open Questions #1), and the full negative-test suite `transfer.test.mjs`/
   `compliance.test.mjs` already carry, extended to the new hasher.
2. Deciding whether the domain-tag hashes are worth revisiting with
   custom-generated t=5/t=6 Poseidon2 parameters (Open Questions #2) before
   writing them off entirely — tonight only evaluated the arities this one
   vendor library ships.

Re-ranked to `EXPERIMENTS.md`: "Port the Merkle accumulator to Poseidon2
compression mode" becomes a new, narrowly-scoped, high-confidence queue item
(the number is already known — this experiment need not repeat the
measurement, only do the integration and re-audit).

## Where this could be used

- **Any Circom/Groth16 Merkle-accumulator circuit** (nullifier sets,
  commitment trees, credential trees) using a 2-to-1 Poseidon compression
  function per level — the compression-mode win here isn't Veil-specific;
  it's a property of Poseidon2's smaller minimum permutation size for a
  2-to-1 compressor, and applies identically to Tornado-style mixers,
  zk-rollup state trees, or any UTXO-shielded-pool design with a
  depth-N accumulator.
- **A thesis chapter on hash-function selection for ZK accumulators**
  specifically benefits from the *negative* result here: most Poseidon2
  writeups cite the compression/sponge win without noting that a
  domain-separated multi-input hash whose arity doesn't land on a supported
  state size can come out worse, not better. That's a citable, measured
  counterexample to "just swap to Poseidon2," useful anywhere protocol
  designers are choosing hash arities for Poseidon2-based circuits from
  scratch — the arity choice matters as much as the hash-function choice.
- **Confidential payroll on Sui with a t-of-n auditor board** (the same
  framing as the 2026-07-22 report): if that design uses a credential
  Merkle tree of any real depth, this experiment's Merkle-only-swap number
  is a direct, reusable input to that system's own proving-time budget.

## Open questions (next queue)

1. **Soundness of the compression-mode construction for Veil specifically.**
   `out = perm(t=2)(a, b)[0] + a` is TACEO's own construction, used in their
   audited `binary_merkle_root.circom` — but Veil's `merkle_proof.circom`
   currently uses `Poseidon(2)` as a *hash*, not a Miyaguchi–Preneel-style
   *compression function*; before a real port, someone needs to write out
   why `perm(a,b)[0] + a` is collision-resistant as a 2-to-1 compressor
   under the same assumptions the paper claims (not just "it's what the
   audited repo does"), and confirm it doesn't introduce a new algebraic
   relation between sibling nodes that the current raw-hash construction
   didn't have. Not done tonight — this is exactly the "soundness argument"
   a real circuit-change PR needs, and it wasn't in scope for a
   benchmark-only night.
2. **Custom t=5/t=6 Poseidon2 parameters for the domain-tag hashes.** Would
   close the −4.1%-to-+99%-loss gap for N=3 and N=4 real-input hashes if the
   padding-to-t=8 cost turns out to be avoidable with a purpose-generated
   permutation at the exact arity Veil needs — genuinely unmeasured
   (UNMEASURED), multi-night scope (see Approach, "What I rejected").
3. **Browser/WASM proving-time delta for the Merkle swap**, extending
   tonight's Node-only benchmark the same way the 2026-07-22 report's
   browser harness extended its Node numbers — cheap follow-up once the
   Node number above exists.
4. Does the −6.35%-per-proof Merkle win compound meaningfully at the
   Merkle-accumulator-scaling queue item (10^5–10^7 commitments, item #4)?
   A cheaper per-level hash doesn't change tree depth, but it does change
   the constant factor on every future experiment that touches the
   accumulator — worth citing this report's numbers there rather than
   re-measuring.
