# 2026-09-30 — Poseidon2 vs circomlib Poseidon: constraint cost (queue #2)

Branch `research/2026-09-30-poseidon2-constraint-cost`. Verdict: **REJECT** as a prover-time lever
(measured, structural — see caveats). Queue #1 (on-chain gas) was attempted first and is still
**BLOCKED**; see "Gas unblock attempt".

## Hypothesis

Replacing every circomlib `Poseidon(N)` in `transfer.circom` with a Poseidon2 (x^5, t∈{2,3,4})
permutation reduces `transfer.circom`'s R1CS constraint count — the number that dominates Groth16
proving time — by at least 15% (baseline 13,611).

Falsified: −3.0% (13,611 → 13,206).

## Threat / privacy model

This is a cost experiment, not a security change; no circuit in `circuits/` was modified. The adversary
model is unchanged (chain observer, colluding relayer, malicious auditor — `docs/threat-model.md`
STRIDE entries unchanged). For completeness, what a *real* Poseidon2 adoption would additionally
require, none of which was done here:

- **Not defended / not analysed:** Poseidon2's security margin against algebraic attacks for these
  parameters (I used R_F=8, R_P=56 for BN254 x^5 from memory of the reference instances, not
  re-derived), and the domain-separation semantics of putting the tag in the capacity lane. A
  circuit change would need the soundness argument, leakage analysis and negative test the loop
  requires; it was not attempted because the measured gain does not justify it.
- **Assumptions:** none new. Constants in `scripts/bench/poseidon2/poseidon2_structural.circom` are
  placeholders — the resulting circuit is **not a secure hash** and must never be used as one.
  R1CS cost depends on structure (S-box count, linear-layer shape), not on constant values.
- Off-chain consequences of a swap (not measured): the frontend/`scripts` circomlibjs hashing,
  every deployed commitment and Merkle root (all existing notes would be orphaned — hard migration).
  `contracts/sources/*.move` performs no Poseidon hashing on chain (roots/commitments are opaque
  bytes; hashing only occurs inside circuits), so the contract would not need a Poseidon2 primitive.

## Approach

Built `scripts/bench/poseidon-constraints.mjs` + `scripts/bench/poseidon2/poseidon2_structural.circom`:

- **Part A** standalone `Poseidon(N)` vs `Poseidon2Shim(N)`, N=1..5.
- **Part B** the three real circuits, unmodified vs every `Poseidon(N)` (incl. the 20 Merkle-path
  hashers) swapped for `Poseidon2Shim(N)` (drop-in interface).
- **Part C** `MerkleProof(depth)` cost by depth.

Shim design: only standardised Poseidon2 widths t=2,3,4 exist (no t=5/6), so N≤3 uses one t=N+1
permutation; N=4 (`Poseidon(4)` commitments/nullifiers) puts the domain tag in the capacity lane
of one t=4 permutation; N=5 (compliance leaf) needs two t=4 permutations (sponge rate 3).

Rejected before building: a real, constants-correct Poseidon2 (would need the reference round
constants, not obtainable here — cross-repo fetch out of scope; unnecessary for a cost measurement);
measuring prover time via a fresh zkey (a swapped circuit needs consistent Poseidon2 witness values
generated by a second implementation — larger than the night's budget; constraints are the proxy,
see caveats).

## Results

Circom compiler here: `circom2` npm package (circom 2.2.3, WASM) — baseline was 2.2.2 built from
source; unmodified constraint counts reproduce the 2026-07-22 baseline exactly (13,611 / 12,743 / 3,058).
Command: `node scripts/bench/poseidon-constraints.mjs --circom <path-to-circom2>` (needs `npm ci` in `circuits/`).

| Circuit | Baseline constraints | Poseidon2 shim | Δ | Non-linear (base → shim) |
|---|---|---|---|---|
| `transfer` | 13,611 | 13,206 | −3.0% | 6,470 → 6,302 |
| `withdraw` | 3,058 | 2,684 | −12.2% | 1,465 → 1,354 |
| `compliance` | 12,743 | 13,107 | **+2.9%** | 6,057 → 6,201 |

Per-instance and structural findings (from the raw output below):

- Poseidon2 has essentially **the same S-box count** as circomlib Poseidon at equal t
  (Poseidon(2): 243 vs 240 non-linear). Its speedups are in the linear layers, which cost R1CS
  constraints only marginally under circom's default optimisation. At `--O2` the standalone counts
  are identical or slightly worse for Poseidon2 at N≤3.
- The only real saving is at N=4 (t=5 → t=4, 300 → 264 non-linear); it is cancelled where N=5 needs two
  permutations (324 → 528). Compliance's leaf hash `Poseidon(5)` is why it gets worse.
- **The Merkle path dominates:** `MerkleProof(20)` is 4,920 non-linear / 10,400 total constraints, i.e.
  76% of `transfer.circom`'s non-linear and total count; each level costs 246 non-linear / 520 total
  and this is linear in depth. The hash choice barely moves it (−3 constraints per level).

## Verdict

**REJECT** — Poseidon2 is not a meaningful prover-time lever for Veil: −3% on transfer, +3% on
compliance, on structure alone. No PR-merge of circuit changes; branch kept. `BASELINE.md` gains the
Merkle-share rows (new measured facts, not a protocol change).

## Where this could be used

- **Any Circom/R1CS Merkle-membership protocol** (Tornado-style pools, Semaphore-like group
  membership, Sui/Aptos shielded pools): the result generalises — in R1CS, tree depth × per-level
  hash, not hash family, sets cost. A confidential-payroll-on-Sui deployment with a large employee
  set should budget for ~520 constraints per tree level.
- **Thesis chapter:** "Where do constraints go in a compliance-carrying shielded transfer" — a cost
  attribution chapter contrasting R1CS with Plonkish/Halo2 arithmetisations, where Poseidon2's
  cheaper linear layers actually pay off.
