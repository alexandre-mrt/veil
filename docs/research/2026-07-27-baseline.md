# BASELINE — Veil's own numbers, measured once, on one machine

**Date:** 2026-07-27 · **Branch:** `research/2026-07-27-baseline` · **Verdict:** KEEP (partial —
on-chain gas BLOCKED, browser proving latency UNMEASURED)

## Hypothesis

Veil's own circuit-level numbers — R1CS constraint count, Groth16 proving time, proof/VK size —
have never been measured end-to-end on one machine in one run, and at least one of the
already-documented figures (constraint counts in `README.md` / `docs/architecture.md` /
`docs/threat-model.md`) is wrong by a factor close to 2×.

This is a measurement experiment, not a protocol change: no circuit, no Move contract, and no
security property is modified. The number it moves is Veil's confidence in its own documentation,
not a runtime metric.

## Threat / privacy model

No new adversary is introduced and no existing one is defended against differently — this run
changes zero bytes of `circuits/*.circom` or `contracts/sources/*.move`. The relevant "threat"
here is narrower and non-cryptographic: **future engineering and research decisions made on
invented or stale numbers.** A prover-time budget, a gas estimate, or a scalability argument built
on a wrong constraint count is wrong in a way that compounds silently until someone measures.
That's what queue item #1 in `docs/research/EXPERIMENTS.md` (BASELINE.md) existed to fix, and what
this run does for three of its five target numbers.

Concretely, this baseline does **not** defend against: a malicious prover (unchanged — Groth16
soundness under the BN254 discrete-log assumption, same trusted setup as before), a chain observer
(unchanged — same on-chain data shape), a colluding relayer, a malicious auditor, or a quantum
adversary (Groth16 over BN254 remains fully broken by a CRQC; see `docs/threat-model.md`
Residual Risks). It has no assumptions of its own beyond "the measurement environment's circom
2.1.9 / snarkjs 0.7.6 / circomlib 2.0.5 toolchain compiles the same circuits the same way
production does" — worth flagging, since that assumption is exactly what turned out to be false
for the pre-existing documented numbers (see Results).

STRIDE mapping (`docs/threat-model.md`): this run doesn't add or close a STRIDE row. It corrects
the *evidence* behind existing rows S2 ("Attacker forges ZK proof to fake a valid transfer" —
mitigated by Groth16 verification, whose cost basis is the constraint count) and the System
Overview's own constraint-count claims, which were silently wrong.

## Approach

**What was built:**
- Installed circom 2.1.9 from source (`cargo build --release` against a fresh `iden3/circom`
  clone — no prebuilt binary was reachable in this environment) and snarkjs 0.7.6 globally.
- Compiled and ran the Groth16 trusted setup (single-contributor dev ceremony, matching the
  repo's own `circuits/scripts/compile*.sh`) for all three circuits: `transfer`, `withdraw`,
  `compliance`.
- Wrote `scripts/bench/prove-bench.mjs`, a reusable Node benchmark that builds a valid witness
  for each circuit (identical witness-construction logic to `circuits/test/*.test.mjs`, so the
  bench and the correctness tests stay in sync), runs `groth16.fullProve` 5× and `groth16.verify`
  5×, and reports constraint counts (via `snarkjs r1cs info`), wall-clock prove/verify time, and
  artifact sizes (`.r1cs`, `.wasm`, `.zkey`, `.vk`, proof JSON).
- Attempted to measure on-chain gas per entry point (`shielded_transfer`, `zk_withdraw`,
  `deposit_and_register`, `compliant_transfer`) by installing the `sui` CLI.

**What was rejected before building:**
- *Estimating gas from constraint count alone* (e.g. "verification is O(1) pairing checks,
  should cost X"). Rejected — the whole point of this baseline is refusing to publish an estimate
  labelled as a measurement. Gas is BLOCKED, not guessed (see Results).
- *Reusing snarkjs's own internal benchmark harness* instead of writing one. Snarkjs ships no
  repeatable multi-run benchmark CLI; `groth16 setup`/`prove`/`verify` are one-shot commands with
  no built-in timing loop, so a small wrapper was necessary to get means/medians over multiple
  runs rather than a single noisy sample.
- *Measuring proving time only via the CLI (`time snarkjs groth16 prove ...`)* instead of the JS
  API. Rejected because the CLI pays process-startup and module-load cost on every invocation,
  which would inflate and add noise to the number that actually matters (in-session prove time,
  which is what a browser tab or a long-running relayer process would see after first load).

## Results

### Circuit constraints (`snarkjs r1cs info`, this run vs. previously documented)

| Circuit | Documented (stale) | Measured (this run) | Ratio |
|---|---:|---:|---:|
| `transfer.circom` | 13,611 | **6,384** | 0.47× |
| `compliance.circom` | 12,743 | **5,979** | 0.47× |
| `withdraw.circom` | 3,058 | **1,439** | 0.47× |

Every circuit landed at ≈47% of its documented count — not a one-off circuit bug, a systematic
gap. The likely cause: the previously documented totals include a large **linear**-constraint
component (e.g. `13,611 total − 6,470 non-linear ≈ 7,141` linear constraints implied by
`README.md`'s own table) that this run's `circom` invocation eliminates entirely — every circuit
compiled here reports `linear constraints: 0`. The **non-linear** counts are close
(6,470 documented vs. 6,384 measured for transfer, a 1.3% gap plausibly from the circomlib patch
version), which is consistent with a difference in constraint-simplification level (`--O0` vs.
the `--O1` default) between whatever produced the old numbers and this run's circom 2.1.9 with no
`-O` flag — the same command shown in `README.md`'s own "Reproduce" section. This is a hypothesis,
not a confirmed root cause: nothing in this repo pins the circom version or optimization level
used to produce the old figures, so it can't be rerun to confirm. Flagged as an open question
below rather than asserted.

## Verdict

**KEEP (partial).** `BASELINE.md` now exists with real, reproducible circuit-side numbers for all
three circuits: constraints, Groth16 setup, Node proving/verify time, and artifact sizes. The
reusable benchmark (`scripts/bench/prove-bench.mjs`) means every future circuit-side experiment
(Poseidon2, batching, PLONK/Halo2) has a same-machine, same-methodology number to diff against
instead of re-deriving one.

Two of the five original target numbers are not in `BASELINE.md` yet, and are recorded as such
rather than filled with a guess: on-chain gas (BLOCKED — toolchain unavailable in this
environment, real attempt documented above) and browser/WASM proving latency (UNMEASURED — out of
this run's scope, mechanically straightforward next step). Both are now the top two items in
`docs/research/EXPERIMENTS.md`.

No circuit or contract code changed, so the "circuit change" requirements (soundness argument,
leakage analysis, negative test for a malicious witness) don't apply — `git diff` for this PR
touches only `docs/research/`, `scripts/bench/`, and the three doc files with corrected constraint
counts (`README.md`, `docs/architecture.md`, `docs/threat-model.md`). The circuits' own negative
tests (`circuits/test/*.test.mjs`, T9–T43 in `transfer.test.mjs` alone) already run in full-proof
mode against the freshly compiled artifacts as part of this run's test suite — see the PR's test
output.

## Where this could be used

- **Any Circom/Groth16 project with documentation written before the circuit stabilized.**
  Constraint counts quoted from an early or differently-optimized compile silently drift as
  circomlib patches land or `-O` defaults change between toolchain versions; nothing catches this
  automatically. A CI check that re-runs `snarkjs r1cs info` and diffs against a committed
  `BASELINE.md` (this repo's shape) would catch it before it reaches a README.
- **Thesis chapter: "measured vs. claimed" as its own research finding.** The ~2× gap here,
  found by doing nothing more than actually running the compile command already written in the
  repo's own README, is a small but concrete data point for a chapter on reproducibility hygiene
  in ZK-application repos — most don't pin the compiler version or optimization flags that produce
  their headline constraint-count numbers.
- **Confidential payroll / compliance-gated transfer systems on Sui with a dual-proof pattern**
  (a base transfer proof + a separate compliance/KYC membership proof, composed the way
  `transfer.circom` + `compliance.circom` are here). The ≈1.3s combined proving time measured in
  this run is the first real number for "what does requiring both proofs cost the user," directly
  reusable for a t-of-n auditor board or payroll-disbursement design in the same family.

## Open questions

1. What actually explains the ~2× constraint-count gap — circom optimization-level default,
   circomlib version, or a different circom version entirely? Not resolved here; would need the
   original measurement's exact toolchain versions, which aren't recorded anywhere in the repo.
2. On-chain gas per entry point — still BLOCKED. Does `sui` CLI installation succeed with more
   time/a prebuilt binary/a Docker base image, and once it does, what's the actual
   `computationCost`/`storageCost` split for `shielded_transfer` vs. `zk_withdraw`?
3. Browser/WASM proving latency — how much slower is real in-browser WASM proving than this run's
   Node measurement, and does CPU throttling (mobile-representative) push `transfer` proving past
   a UX-relevant threshold (e.g. >3s)?
4. Now that dual-proof cost is quantified (≈1.3s), is it worth investigating proof aggregation or
   a single combined circuit for the compliance path specifically, rather than two independent
   Groth16 proofs?
