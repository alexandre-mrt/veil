# Baseline — Veil's real cost profile, measured once, on one machine

**Queue item:** #1 `baseline` (`docs/research/EXPERIMENTS.md`)
**Base commit:** `9f2e921` (`origin/main`, 2026-07-14)
**Environment:** sandboxed CI container, no GPU, Node v22.22.2, circom2 (WASM) 0.2.23 / circom
compiler 2.2.3, snarkjs 0.7.6, headless Chromium 1194 (Playwright 1.56.1).

## Hypothesis

Veil's own numbers — per-circuit constraints, proving time, proof/VK size, on-chain gas, browser
proving latency — have never been measured together in one run, and at least one of them will
contradict what the project's own docs claim. **Falsifiable form: re-measuring `transfer.circom`'s
constraint count and public-input count from the current `main` source will match `docs/SPEC.md` and
`CLAUDE.md`.** (It does not — see Results.)

## Threat / privacy model

This is a measurement experiment, not a new mitigation, so there is no new adversary being defended
against. But the *finding* below has a concrete adversary of its own, so it's stated properly:

**Adversary: nobody, by design — a broken build pipeline that nobody has actually run end-to-end.**
What they can do: nothing malicious is required. What they observe: the checked-in
`frontend/public/circuits/transfer_vk.json` (6 public inputs) does not match the verifying key
implied by current `main`'s `transfer.circom` (7 public inputs, since it added a Merkle
anonymity-set membership proof) or `contracts/sources/pool.move`'s hard assertion
(`public_inputs_bytes.length() == 224`, i.e. 7 × 32 bytes — `pool.move:187`). If someone deployed the
current frontend circuit artifacts as-is, `groth16.fullProve` would need `merkleRoot` +
`pathElements[20]` + `pathIndices[20]`, none of which the shipped VK's shape expects, and any proof
built against the *old* 6-input VK would be rejected on-chain by the length assertion before the
Groth16 verifier even runs.

**What this does not defend against:** nothing — it's a report, not a fix. The stale artifacts are
still stale after this experiment; see Verdict and Open Questions for what closes the gap.

**Assumptions:** the Groth16 trusted setup here is a single throwaway dev contribution
(`circuits/scripts/compile.sh`'s own comment: "Single dev contribution — for testing only"), same as
production `circuits/build/`. No new trust assumption introduced.

**STRIDE mapping (`docs/threat-model.md`):** closest to **Tampering** (the deployed proving
artifacts and the on-chain verifier's expected input shape have silently diverged — not from an
attacker, but the failure mode if unnoticed is the same: proofs built against the shipped frontend
artifacts would never verify) and **Repudiation-adjacent** (a broken artifact pipeline means nobody
can currently produce a valid end-to-end proof to audit against the deployed verifier).

## Approach

**What I built:**
1. A reusable benchmark, `scripts/bench/circuit-baseline.mjs` — builds a real constraint-satisfying
   witness for `transfer.circom` (including a valid depth-20 Merkle membership proof, all-zero
   sibling path) and measures Groth16 setup → proving → verify → sizes, in Node.
2. `scripts/bench/browser-proving-bench.mjs` + `scripts/bench/www/index.html` — same proof, driven
   inside headless Chromium via Playwright, to get a real (not estimated) browser-vs-Node delta.
3. Ran the project's own test suites (`circuits/test/*.test.mjs`, `scripts/src/test-converter.ts`)
   against freshly compiled artifacts, for real — see Results for why this was not a no-op.

**Toolchain substitution (disclosed up front):** the native `circom` binary specified in `CLAUDE.md`
("Circom 2.1 + snarkjs 0.7") could not be installed — `cargo install circom` fails
(`circom` is not published on crates.io as an installable binary crate), and the GitHub release
asset (`github.com/iden3/circom/releases/...`) returns `403 Forbidden` from this session's egress
proxy (confirmed org policy denial, not a transient error — see raw output below). I used
[`circom2`](https://www.npmjs.com/package/circom2) instead: a WASM build of the same circom 2.x
compiler, installable directly from `registry.npmjs.org` (which this session can reach directly).
`npx circom2 --version` reports **"circom compiler 2.2.3"** — a real circom compiler, not a
reimplementation, so constraint counts should be compiler-faithful; the r1cs numbers below were
cross-checked against `snarkjs r1cs info` independently and agree exactly. Flagged as a caveat
regardless: the deployed testnet package was built with the native binary, and I have not verified
byte-for-byte r1cs equality between the two toolchains.

**Alternatives rejected:**
- Building native `circom` from source via `raw.githubusercontent.com` (reachable, unlike
  `github.com` release assets) — rejected. The 403 on `github.com` release downloads is an explicit
  org egress policy signal (see `/root/.ccr/README.md`: "do not retry or route around it — report the
  blocked host"); fetching the same source through a different GitHub subdomain would be routing
  around that decision in spirit, not just in mechanism.
- Installing `sui` via `cargo install sui` or a GitHub release — both routes go through hosts already
  confirmed policy-denied while testing `circom` (`static.crates.io` → 403, a `github.com/.../releases/download/...`
  asset → 403); `sui`'s release binary lives at the same URL shape, so the same block applies — not
  re-tested against the literal `sui` URL, to avoid re-poking a host already confirmed blocked. No apt
  package, no cached binary anywhere on the filesystem. On-chain gas is marked `BLOCKED`, not estimated.
- Reusing gas numbers from `docs/` or old deployment logs for the on-chain figures — rejected per the
  one rule: a number I did not measure this session does not go in a "measured" table, however
  plausible.

Cold start (first page load, wasm/zkey fetched over local HTTP + wasm instantiation) costs **~2.2×**
the warm proving time. Warm-browser proving (~1.5–1.7 s) is close to Node's 1.5 s on the same CPU —
the wasm witness calculator, not the JS engine, dominates. This is desktop headless Chromium on this
container's CPU, not a mobile device; mobile proving latency is `UNMEASURED`.

### Test suites — run for real against freshly compiled artifacts

```
$ cd circuits && node --experimental-vm-modules test/transfer.test.mjs
=== Veil Transfer Circuit Tests (v2 — audit fixes) ===
Mode: FULL PROOF (snarkjs Groth16)
  [FAIL] T1: Genesis transfer (cumOld=0, randOld=0, first-ever transfer)
         Not all inputs have been set. Only 13 out of 54
  ... (13 failures total, all "Not all inputs have been set. Only 13 out of 54")
=== Results: 27 passed, 13 failed ===
```
Root cause, confirmed by reading the source: `buildValidWitness()` in `transfer.test.mjs` was never
updated after `transfer.circom` grew its Merkle membership proof (`merkleRoot`, `pathElements[20]`,
`pathIndices[20]` — 41 new signals). It supplies 13 of the 54 required signals; every "happy path"
test that needs a real proof throws before it can assert anything. The 13 constraint-*rejection*
tests still pass, coincidentally — `fullProve` throwing on missing inputs also satisfies "proof
generation must fail." This has been silently vacuous for the project's entire history: the suite
only runs in `FULL_PROOF_AVAILABLE` mode when `circuits/build/` exists, which it never has in CI
(circom was never installed there either) — so this is the **first time these 40 tests have ever
run against a real proof**, and 13 of them have been broken since whenever the Merkle proof was
added.

```
$ node --experimental-vm-modules test/compliance.test.mjs
=== Results: 30 passed, 0 failed ===
$ node --experimental-vm-modules test/withdraw.test.mjs
=== Results: 35 passed, 0 failed ===
```
`compliance.circom` and `withdraw.circom`'s test files *were* kept in sync with their circuits — this
is an isolated regression in `transfer.test.mjs`, not a systemic pattern. (105 real circuit tests
run tonight, not the "40" `CLAUDE.md` cites — the project grew two more circuits since that line was
written.)

```
$ cd scripts && bun install && bun run src/test-converter.ts

```
Matches `CLAUDE.md`'s claim exactly. One live-fire note, not a failure: the passing test
`"Veil 6 inputs → 192 bytes"` is a generic layout test using 6 as an illustrative circuit size — it
is not asserting anything about the *current* `transfer.circom` (which is 7 inputs / 224 bytes now),
but its comment reads as if it does. Same drift pattern as the doc/VK gap above, in a place that
doesn't actually break anything.

## Verdict: **PARK**

Not `KEEP` (there is no circuit change to keep) and not `REJECT` (the baseline itself is not a
proposal that can lose). `BASELINE.md` is written and merges with this PR — that part is done and
becomes the standing reference for every future comparison. It's `PARK` because the experiment
surfaced a concrete, unresolved gap (stale `transfer.circom` test/deploy artifacts) that is real work,
not a follow-on research question, and is blocked on nothing except someone doing it — see Open
Questions and the new `EXPERIMENTS.md` entry.

**Full-suite status going into this PR: RED.** `circuits/test/transfer.test.mjs` fails 13/40 for
real, reproducibly, against the current `main` circuit — not something introduced by this change,
but true right now on `main` and now provable for the first time. Per the nightly loop's own rule
("never loosen, skip, or fudge a test to get to green"), this is **opened as a draft PR**, not a
normal one, with the failure and root cause above.

## Where this could be used

- **Any Circom/snarkjs project whose CI has never had `circom` installed.** The pattern here —
  hash-only fallback tests that silently never exercise the real prover, so a source change to public
  inputs can go undetected indefinitely — is generic, not Veil-specific. Worth a lint: "does this repo's
  CI ever produce a `.zkey`? If not, its 'full proof' tests are dead code."
  `circom2` (WASM, npm-installable) is a direct fix for locked-down CI/sandboxed environments that
  can't reach `github.com` release assets or `crates.io` — e.g. this exact Claude Code sandbox
  profile, or any air-gapped/allowlisted CI runner.
- **Thesis chapter on ZK build-pipeline integrity**, not just circuit soundness: the commitment
  scheme was correct throughout (no `assertRejected` test failed), but the *build artifact* (the
  frontend's committed VK) drifted from the *source of truth* (the circuit) without any test catching
  it, because the test that should have caught it degrades silently instead of failing loud when its
  prerequisites are missing. That's a supply-chain-adjacent finding worth a paragraph independent of
  Veil.
- **Any protocol doing confidential payroll / compliance-gated transfers on Sui** — the constraint
  and gas numbers here (13,611 constraints, ~1.5 s Node proving, 128-byte on-chain proof) are the
  right order-of-magnitude reference point for anyone estimating whether a similar Poseidon +
  Merkle-membership + range-proof circuit fits their latency budget, before they've built anything.
