# 2026-07-25 — BASELINE: Veil's own numbers, measured once, on one machine

Queue item #1 (`docs/research/EXPERIMENTS.md`). Night one of the research loop —
`docs/research/` did not exist before this run.

## Hypothesis

Veil's per-circuit R1CS constraint count, Groth16 proving time, proof/VK size, and
on-chain gas per entry point have never been measured together on one machine in
one run. Establishing them now, with commands anyone can re-run, turns every future
"X is faster/smaller/cheaper" claim in this research loop into a real delta instead
of a guess against README prose.

Falsifiable form: **the README's existing constraint-count claims (13,611 / 12,743 /
3,058) are accurate**, and **proving time, proof size, VK size, and on-chain gas can
be measured from a clean checkout without hand-tuning.** The first half is testable
today; the on-chain-gas half turned out to be false in this environment — see
Verdict.

## Threat / privacy model

This experiment changes no circuit, no contract, and no protocol behavior — it only
runs the existing toolchain and records numbers. So the adversary analysis is short
by necessity, but it's still worth being explicit about, because "just a benchmark"
PRs are exactly the kind that get waved through without scrutiny:

- **What a chain observer, colluding relayer, or statistical deanonymiser learns
  from this PR**: nothing new. Constraint counts are already fully derivable by
  anyone from the public `.circom` source (this is why circuit source is not secret
  in a ZK system — soundness lives in math, not obscurity). Proving time and proof
  size are a function of the public circuit and the public snarkjs/circom versions;
  they don't depend on any witness value. Publishing them doesn't narrow anyone's
  guess about a real user's transaction.
- **What it does NOT defend against / residual surface**: measuring on one
  contributor's machine (this sandbox: 4-vCPU Xeon @2.80GHz, Node v22.22.2, linux/x64)
  is not evidence about mobile proving latency, about a different CPU
  microarchitecture, or about proving time under memory pressure from a real
  browser tab with a wallet extension and a dApp loaded. Treat every number below as
  "on this machine, this toolchain version" — not a hardware-independent constant.
- **Assumptions**: circom 2.2.2 (self-built from `iden3/circom` git tag `v2.2.2`,
  since no prebuilt binary was available — see Approach), snarkjs 0.7.6 (already
  pinned in `circuits/package.json`), the existing dev-only single-contributor
  trusted setup (`RR2` in `docs/threat-model.md` — unaffected by this PR, still an
  open pre-mainnet blocker).
- **STRIDE mapping**: none. No control in `docs/threat-model.md`'s Security Controls
  Summary Table changes. This PR is instrumentation, not a mitigation or a new
  attack surface.

## Approach

**What I built:**
1. `scripts/bench/witnesses.mjs` — shared witness builders for all three circuits,
   copied faithfully from `circuits/test/{transfer,compliance,withdraw}.test.mjs`'s
   `buildValidWitness` logic (same domain tags, same depth-20 Merkle path
   construction) so every timed proof is a real accepted witness.
2. `scripts/bench/prove-latency.mjs` — Node benchmark: builds a witness, runs
   `groth16.fullProve` / `groth16.verify` N times per circuit, reports mean ± stddev
   proving/verify time and proof/VK/zkey byte sizes. Writes
   `scripts/bench/out/prove-latency.json`.
3. `scripts/bench/prove-latency-browser.mjs` — same measurement but inside headless
   Chromium via Playwright, loading the actual `snarkjs.min.js` browser bundle the
   frontend ships (not a Node proxy for browser behavior). Serves the wasm/zkey/vk
   over a local HTTP server (fetch() doesn't reliably resolve `file://` in Chromium)
   and times `fullProve`/`verify` with `performance.now()` inside the page.
4. `scripts/bench/run-all.sh` — the one entry point that runs everything below with
   the exact commands, so this report (and every future one) is reproducible.

**What I rejected:**
- *Timing `sui move test` for constraint verification* — not applicable, this is a
  circuit-only measurement; contract gas is a separate, currently-blocked item (see
  Verdict).
- *Using the fallback hash-only mode already in `circuits/test/*.test.mjs`* — that
  mode simulates constraints in JS and does not produce a real Groth16 proof or
  proving time; the README already flags it as "a linting aid, not evidence" after
  it hid a real Merkle-path bug. Real proving mode only.
- *Measuring proving time via the existing test files directly* — they interleave
  43/30/35 proof+verify calls with assertions and negative-test cases whose timing
  is not comparable across circuits; a dedicated benchmark with a fixed iteration
  count and only happy-path witnesses gives a clean, comparable number.
- *A synthetic/random witness instead of the test suite's real one* — would still
  produce a valid proof (proving time depends on constraint count and toolchain, not
  on witness values, for Groth16 over R1CS) but would drift from the actual test
  fixtures over time. Reusing the real builder means this benchmark can't silently
  go stale relative to `circuits/test/`.

Proof size in `proof.json` (~720 B, decimal-string JSON) is not the on-chain size —
`docs/SPEC.md`'s "Proof Layout (128 bytes)" is the arkworks-compressed
little-endian encoding `scripts/src/proof-converter.ts` produces for
`sui::groth16`. 128 bytes is the number that matters for calldata/gas; the JSON
figure here is purely a snarkjs-output-size data point.

Note the two large circuits (transfer, compliance — both ~6,000-6,500 non-linear
constraints) prove in a similar ~900ms band despite an 870-constraint difference,
while withdraw (1,465 non-linear) is ~3x faster — proving time tracks non-linear
(Poseidon-dominated) constraint count roughly linearly at this scale, consistent
with Groth16's O(n log n) FFT-dominated prover cost.

### Proving time in a real browser — headless Chromium (`prove-latency-browser.mjs 10`)

```
$ node scripts/bench/prove-latency-browser.mjs 10
[transfer/browser] prove: 1284.5ms ± 89.8ms (n=10)  verify: 20.67ms ± 2.85ms  proof.json: 722B
  (Node fullProve mean: 952.0ms, browser/Node ratio: 1.35x)
```

Chromium version: 141.0.7390.37 (headless, Playwright 1.56.1, same wasm/zkey
artifacts as the Node run, same `snarkjs.min.js` bundle the frontend's proving Web
Worker uses). Only `transfer.circom` was benchmarked in-browser — it's the circuit
users prove most often and the one with the highest constraint count, so it's the
worst case for UX latency.

**Caveat, stated plainly**: this is headless Chromium in a sandboxed VM, not a
phone, not even a real desktop browser tab with extensions and a wallet loaded. An
earlier run of this same script, taken while three orphaned benchmark processes
from a prior step were still silently competing for this box's 4 vCPUs (see the
"operational note" under Full test suite below), measured a 2.01x browser/Node
ratio; the clean re-run above — after those processes were killed — measured 1.35x.
Both are "real" in the sense that the script did what it says, but only the 1.35x
figure reflects steady-state, uncontended hardware; the ratio itself is sensitive
enough to system load that it should be read as "roughly 1.3-2x on this machine,"
not a precise constant. "WASM proving latency on mobile" (`EXPERIMENTS.md` item 10)
remains unmeasured — a
CPU-throttled variant of this same script is the cheapest next step, not a full
device lab.

**One operational note worth recording**: `transfer.circom`'s 43-case suite
appeared to hang twice during this session — sitting at 11-15% CPU for 6-9 minutes
with zero forward progress (`/proc/<pid>/stat` `utime` not moving across a 5s
sample) before being killed. The first time had a clear, self-inflicted cause:
three earlier `prove-latency.mjs` invocations and one `withdraw.test.mjs` run had
each printed their final result but never exited (a dangling handle in
snarkjs/circomlibjs kept Node's event loop alive past the last `await`), and I'd
backgrounded all of them without noticing they were still fighting for this box's 4
vCPUs — `kill -9`-ing them and re-running produced a clean pass in well under 2
minutes. The second stall happened later with no other Veil process visible in
`ps aux` at the time, so local contention doesn't fully explain it; the most likely
remaining cause is host-level CPU steal time in this sandboxed VM, which isn't
visible from inside the container. Every clean completion — three of them across
this session, including the final one right before this PR was assembled —
produced the identical **43 passed, 0 failed**, so this reads as proving-time
variance under a noisy host, not a correctness issue in the circuit or the test
suite. Lesson for future nights: don't trust an apparent hang without checking
`/proc/<pid>/stat` progress and `ps aux` for stray processes first, and prefer
`process.exit(0)` at the end of one-shot Node benchmark scripts (now fixed in both
`scripts/bench/prove-latency.mjs` and `prove-latency-browser.mjs`) so they don't
linger and become the next contention source themselves.

## Verdict: **KEEP** (partial — on-chain gas measurement is BLOCKED, split into its own queue item)

Four of five planned measurements succeeded with real numbers on real toolchain
output: circuit constraints, Groth16 setup time, proving/verify time + proof/VK
size (Node), and browser proving latency. `BASELINE.md` is created and merged with
everything above.

**On-chain gas per entry point is BLOCKED**, and it's worth being precise about
why, since "install the CLI" sounds trivial and isn't, here:

- No `sui` binary preinstalled, no apt package (`apt-cache search sui` — nothing).
- `sui.io` and `github.com/MystenLabs/sui/releases` (where prebuilt binaries live)
  both return `403` in this session — this session's GitHub access is scoped to
  `alexandre-mrt/veil` only (confirmed via the GitHub API's own error message:
  *"GitHub access to this repository is not enabled for this session"*), so a
  release download is out of scope, not just network-flaky.
- Building `sui` from source is possible in principle (`git clone
  https://github.com/MystenLabs/sui.git` over the git protocol *does* succeed,
  unlike the REST/web API) but Sui is one of the largest Rust workspaces in the
  ecosystem — a full release build is a multi-hour, multi-GB undertaking that does
  not fit a single research-loop night, and re-doing it every night to get gas
  numbers would dominate the loop's entire budget for one metric.

This is exactly the loop's own escape hatch: *"If a toolchain won't install and you
genuinely cannot measure, mark the experiment BLOCKED, write down exactly what was
missing."* Gas is re-queued as its own item (`EXPERIMENTS.md` #2: get `sui` into the
environment — most realistically a prebuilt binary baked into the sandbox image —
and #3: the actual gas measurement, blocked on #2). No gas figure appears anywhere
in `BASELINE.md`; every field that would hold one says `UNMEASURED — see
EXPERIMENTS.md #2/#3`, not a guess.

## Where this could be used

- **Any Circom + Groth16 + Sui project** — `scripts/bench/witnesses.mjs`'s pattern
  (reuse the test suite's own witness builder for benchmarking, don't hand-roll a
  second copy that drifts) and `prove-latency-browser.mjs`'s pattern (serve
  wasm/zkey over a throwaway local HTTP server, drive headless Chromium with
  Playwright, time with `performance.now()` inside the page) are both
  circuit-agnostic — copy-paste into any snarkjs-based project that wants a real
  browser proving number instead of a Node proxy for one.
- **Thesis chapter**: "measuring what you claim" — the gap between README-claimed
  numbers and independently re-derived numbers (here: zero gap, a good sign) is
  itself a methodology point worth a paragraph — self-reported ZK protocol
  benchmarks are common and rarely independently reproduced in the same repo they
  describe.
- **Any protocol evaluating Groth16 vs PLONK/Halo2** (queue item 7) — this baseline
  is the "before" column that migration decision needs; without it, a future
  "PLONK is worth the trusted-setup removal" argument has nothing to be measured
  against.
