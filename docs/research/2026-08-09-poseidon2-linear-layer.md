# Poseidon2's cheap linear layer: does it move Veil's R1CS constraint count or proving time?

## Hypothesis

Replacing Poseidon's dense t×t MDS matrix multiplication in circomlib's full rounds with a
Poseidon2-style sparse/cheap linear construction (the specific mechanism Poseidon2 is marketed on:
"O(t) field multiplications instead of O(t²)") reduces Veil's per-hash R1CS constraint count and
Groth16 proving time by a measurable, nonzero amount, for the arities Veil actually uses (t=3 for
the depth-20 Merkle node hash, t=5 for commitment/nullifier hashes).

## Where this sits in the queue

Queue item #2 (`docs/research/EXPERIMENTS.md`), ranked directly behind on-chain gas measurement.
Item #1 was re-attempted first (see "On-chain gas — still blocked" below) and remains blocked for
the same fundamental reason as 2026-07-22, so this experiment took the slot.

This is **not** an attempt to port Veil's circuits to a validated Poseidon2 instance. That would
require official, audited BN254 round constants and internal/external matrices (Grassi/
Khovratovich/Schofnegger's reference parameters, generated by a sage script and cross-checked
against the reference implementation) which this session could not fetch or independently verify
(see Approach, "What was rejected"). Instead this isolates the one falsifiable, self-contained
technical question the queue item actually cares about: *in circom + Groth16, does linear-layer
term density affect R1CS constraint count at all?* That question is answerable without needing
audited Poseidon2 parameters, and its answer determines whether a full migration is worth pursuing
in the first place.

## Threat / privacy model

**Concrete adversary:** none, directly. Nothing in this experiment is wired into `transfer.circom`,
`compliance.circom`, `withdraw.circom`, or any Move module or deployed package. The four probe
circuits (`circuits/bench/t3_dense.circom`, `t3_cheap.circom`, `t5_dense.circom`, `t5_cheap.circom`)
are compiled, proved, and verified entirely locally, with locally generated dev-only zkeys against a
throwaway `pot10` ptau (`circuits/bench/build/pot10_final.ptau`, not committed — regenerable, see
Approach). No proof, verification key, or artifact from this experiment is submitted to any chain,
committed as a production artifact, or reachable by any user, relayer, or auditor.

**What a chain observer learns:** nothing. There is no on-chain change. Pool state, commitment
structure, nullifier structure, and the deployed `transfer_vk`/`withdraw_vk`/`compliance_vk` are
byte-for-byte unchanged (verified in Results — production R1CS constraint counts and all 108 circuit
tests are unchanged from `BASELINE.md`).

**What this does NOT defend against / residual surface:** this experiment says nothing about
soundness margins. The probe circuits reuse circomlib's real Ark round constants and Sigma S-box
(so the *S-box* portion is exactly as sound as production Poseidon), but the "cheap" variant's
linear layer (`MixCheap`: `out[i] = sum(in) + in[i]`, the circulant(2,1,1,...) matrix — Poseidon2's
actual published t=3 external matrix, generalized to t=5 without a published reference) is paired
with round constants and a round count (`nRoundsF=8`, `nRoundsP` from circomlib's table) that were
derived and validated for the *dense* matrix, not for this one. Whether `MixCheap` with these
specific round constants meets Poseidon2's claimed 128-bit security margin is **not established by
this experiment and not claimed**. This is fine for what's being measured (R1CS mechanics are
independent of the specific constant values used, only their *count* per linear combination — see
Approach) but means the probe circuits must never be treated as a drop-in secure hash.

**Assumptions:** BN254 scalar field, Groth16 soundness under the discrete-log assumption (same as
production), circom 2.2.2's default `--O1` optimization level (the same level `compile.sh` uses for
production circuits — no flag override).

**STRIDE mapping (`docs/threat-model.md`):** none. This experiment changes no deployed security
property, so it does not touch any S/T/R/I/D/E row. Its relevance is to the queue's "scalability"
axis (prover time is a cost Veil pays on every transfer/withdrawal/compliance proof), not to a
specific threat-model entry — closest tangential row is D2/D3 (griefing cost), and as the Results
below show, that tangential relevance turned out not to materialize either, since constraint count
(and therefore rough per-proof cost) doesn't move.

## Approach

**What was built.** `circuits/bench/linear_layer_probe.circom` defines `LinearLayerProbe(nInputs,
dense)`: `nRoundsF + nRoundsP` rounds of (round-constant addition; Sigma x⁵ S-box on all `t`
elements for full-round positions, on element 0 only for partial-round positions; a linear mix),
using the real `t`, round schedule, and `POSEIDON_C` round constants from
`circomlib/circuits/poseidon_constants.circom` for `Poseidon(2)` (t=3) and `Poseidon(4)` (t=5) — the
two arities Veil actually calls (`merkle_proof.circom:28`, `transfer.circom:66/75/115`,
`withdraw.circom:59/91/105`). The `dense=1` branch mixes with `MixDense` (circomlib's real
`POSEIDON_M(t)` MDS matrix, `t` terms per output row — literally the same linear algebra circomlib's
own `Mix` template does). The `dense=0` branch mixes with `MixCheap` (`out[i] = sum(in) + in[i]`,
2 additions instead of `t` constant multiplications). Everything else — round constants, S-box,
round count, round-boundary logic — is byte-identical between the two branches. Four entry circuits
(`t3_dense`, `t3_cheap`, `t5_dense`, `t5_cheap`) instantiate these.

This deliberately does not reproduce circomlib's `MixS`/`P`-matrix sparse trick for partial rounds:
that trick is a decomposition specific to the dense `M` it's derived from, and re-deriving an
equivalent decomposition for `MixCheap` was exactly the "needs official/audited derivation" step
this session couldn't complete offline. Applying a uniform full-density-style mix at every round
position (partial included) in *both* branches keeps the comparison apples-to-apples without
requiring that derivation, at the cost of the probe circuits' absolute constraint counts not
matching production `Poseidon(nInputs)`'s counts from `BASELINE.md` (they're not supposed to — see
Results).

**What was rejected.**

- *A full Poseidon2 port of the three production circuits.* Rejected for two reasons: (1) it would
  be exactly the kind of "circuit change swapped into production, deployed" move the task rules
  require a soundness argument for — and no official BN254 Poseidon2 round constants/matrices were
  reachable this session to build that argument on (see below); (2) it's the wrong order of
  operations — better to answer the narrower mechanical question first and let the answer decide
  whether the larger port is worth attempting at all.
- *Fetching official Poseidon2 BN254 parameters.* The `poseidon2` npm package (v0.4.2, MIT,
  zero-dependency TS implementation) was pulled from `registry.npmjs.org` (an allowed host) and
  inspected — it ships worked instances for Goldilocks-12 and Vesta-3 only, not BN254. Its own
  `CUSTOM_FIELD_T.md` points to `github.com/HorizenLabs/poseidon2`'s precomputed-constants directory
  and a sage script to generate new ones. Fetching either was not attempted: this session's GitHub
  access is explicitly scoped to `alexandre-mrt/veil` only (`api.github.com` returns `"GitHub access
  to this repository is not enabled for this session"` for any other repo), and no `sage` toolchain
  is installed. This is the actual, current blocker on a *validated* Poseidon2 migration — recorded
  as a new queue item rather than worked around with self-generated, unverifiable round constants.
- *Swapping the matrix in place inside `PoseidonEx` itself (production template)* while leaving
  `MixS`/`P` untouched. Rejected — mathematically inconsistent (P and S are derived from M; pairing
  them with a different M produces neither a correct Poseidon nor a correct Poseidon2 permutation,
  just an arbitrary circuit), and would have made the R1CS-mechanics question harder to isolate,
  not easier.

**Toolchain.** `circom` was not installed (fresh container, matches 2026-07-22). Cloned
`iden3/circom` tag `v2.2.2` from `github.com` (reachable — this is a plain open-source dependency
fetch, not a GitHub API call, and unrelated to the repo-scoping restriction above) and built with
`cargo build --release` (`~1m19s`, used by full path, not installed to `~/.cargo/bin`). `circomlib`/
`snarkjs`/`circomlibjs` installed via `npm install` in `circuits/` and `scripts/bench/` (both
`registry.npmjs.org`, an allowed host). Used a `pot10` (2¹⁰) Powers of Tau file instead of the
production `pot15` — the probe circuits (519 / 740 constraints) are far below `pot15`'s ceiling and
a smaller ptau is faster to fetch and set up; same source (`storage.googleapis.com/zkevm/ptau/`,
reachable), same single-dev-contribution Groth16 setup pattern as `compile.sh` (dev-only, not a
production ceremony — not that it matters, since nothing here is deployed).

## Results

### R1CS constraints — dense vs. cheap linear layer, identical everything else

| Circuit | t (arity) | Non-linear constraints | Linear constraints | Total constraints | Wires |
|---|---|---|---|---|---|
| `t3_dense` | 3 | 243 | 276 | 519 | 522 |
| `t3_cheap` | 3 | 243 | 276 | 519 | 522 |
| `t5_dense` | 5 | 300 | 440 | 740 | 745 |
| `t5_cheap` | 5 | 300 | 440 | 740 | 745 |

```
# of Constraints: 519                     # of Constraints: 519

# of Public Inputs: 2                     # of Public Inputs: 2

=== t5_dense ===                          === t5_cheap ===
# of Wires: 745                           # of Wires: 745
# of Constraints: 740                     # of Constraints: 740
# of Private Inputs: 0                    # of Private Inputs: 0
# of Public Inputs: 4                     # of Public Inputs: 4
# of Labels: 2115                         # of Labels: 2115
# of Outputs: 5
```

(Compiler-level constraint counts, from `circom bench/<name>.circom --r1cs --sym --output
bench/build -l node_modules`, matched the `snarkjs r1cs info` numbers above exactly for all four:
e.g. `t3_dense`/`t3_cheap` both report `non-linear constraints: 243`, `linear constraints: 276`.)

This is the expected result once you look at what `circom --O1` (the default, and what
`compile.sh` uses — no override) actually does: "signal to signal and signal to constant
simplification." A linear combination of signals with constant coefficients — which is exactly what
a matrix-vector product against a compile-time-constant matrix is — gets substituted directly into
whatever consumes it (here, the next round's `Sigma` S-box multiplication) rather than materialized
as its own R1CS row, *regardless of how many terms are in the combination*. R1CS constraints are
charged for genuine signal×signal multiplications (the S-box) and for materializing a signal via
`<==` where substitution isn't possible; a linear combination with 5 terms costs exactly the same
as one with 2 terms in that accounting. Poseidon2's headline efficiency claim is about *native*
field-multiplication count, which is a real, different cost model (relevant to STARK/AIR/Plonkish
arithmetizations with per-gate costs, or to plain non-SNARK hashing) — not to R1CS/Groth16 constraint
count.

### Proving time — two independent 30-run trials, one warm-up run discarded per circuit

`node scripts/bench/linear-layer-probe.mjs --runs 30`, `snarkjs.groth16.fullProve`, node v22.22.2,
linux/x64:

| Circuit | Trial 1 mean (σ) | Trial 2 mean (σ) | Trial 1 Δ (cheap − dense) | Trial 2 Δ |
|---|---|---|---|---|
| t=3 dense | 128.14 ms (7.57) | 114.42 ms (7.00) | — | — |
| t=3 cheap | 124.66 ms (10.85) | 112.98 ms (8.74) | −3.49 ms (−2.7%) | −1.44 ms (−1.3%) |
| t=5 dense | 130.71 ms (11.59) | 119.06 ms (10.17) | — | — |
| t=5 cheap | 118.46 ms (8.68) | 118.10 ms (8.72) | −12.24 ms (−9.4%) | −0.95 ms (−0.8%) |

Raw output, trial 1:

```

t3_cheap   mean 124.66 ms  (sigma 10.85, 30 runs)
t5_dense   mean 130.71 ms  (sigma 11.59, 30 runs)
t5_cheap   mean 118.46 ms  (sigma 8.68, 30 runs)

=== Summary ===
t3: dense 128.14ms vs cheap 124.66ms -> delta -3.49ms (-2.7%)
t5: dense 130.71ms vs cheap 118.46ms -> delta -12.24ms (-9.4%)
```

Raw output, trial 2 (immediately following, same process/hardware):

```
t3_dense   mean 114.42 ms  (sigma 7.00, 30 runs)
t3_cheap   mean 112.98 ms  (sigma 8.74, 30 runs)
t5_dense   mean 119.06 ms  (sigma 10.17, 30 runs)
t5_cheap   mean 118.10 ms  (sigma 8.72, 30 runs)

=== Summary ===
t3: dense 114.42ms vs cheap 112.98ms -> delta -1.44ms (-1.3%)
t5: dense 119.06ms vs cheap 118.10ms -> delta -0.95ms (-0.8%)
```

The delta is smaller than one standard deviation in every case, and its magnitude is not
reproducible between trials (t=5's delta moved from −12.24ms to −0.95ms with nothing changed but
re-running). This is consistent with the R1CS finding above: with identical constraint counts, the
Groth16 prover's two dominant MSMs are identical work; whatever's left (the wasm witness-calculator
evaluating fewer field multiplications for `MixCheap`) is too small relative to run-to-run system
noise on this machine to call a measured effect.

12/12 checks behaved as required: neither variant lets a prover claim an output the circuit didn't

or output that still verifies.

## Verdict: REJECT

Swapping Poseidon's dense full-round MDS multiplication for a Poseidon2-style sparse linear layer
does **not** move Veil's R1CS constraint count (measured: exactly zero delta, both arities) and does
**not** produce a reliable, reproducible proving-time improvement (measured: sub-standard-deviation,
non-reproducible delta across two independent trials). The mechanism Poseidon2 is built around —
fewer native field multiplications in the linear layer — is real, but circom's default constraint
simplification already makes Veil's *existing* Poseidon linear layer free in R1CS terms; there is
nothing left for Poseidon2 to save in this specific cost model.

This does not reject Poseidon2 wholesale — see "Where this could be used" below for where the same
efficiency *would* actually pay off — but it does mean **a full Poseidon2 port of Veil's three
production circuits should not be prioritized for the reason originally in the queue** (reducing
Groth16 prover time / constraint count). `BASELINE.md` is unchanged; no production circuit, contract,
or verification key was touched.

## Where this could be used

- **The specific negative result** (R1CS-based Groth16 systems get no constraint-count benefit from
  Poseidon2's linear-layer trick) generalizes to any other circom/Groth16 or general R1CS-based
  Poseidon deployment using an equivalent optimization level — Tornado-Cash-style mixers, other
  Semaphore-derived identity/membership circuits, any Merkle-accumulator privacy pool built the same
  way. Worth knowing before spending engineering time on the same port there.
- **Where Poseidon2's linear layer genuinely would help Veil**: not proving, but *native* (non-SNARK)
  hashing — the indexer/relayer reconstructing the Merkle tree client-side or server-side
  (`scripts/src/compliance-utils.ts`'s `buildMerkleTree`, and any future off-chain accumulator
  indexer per queue item #4), and browser-side witness precomputation before proving starts. Both
  pay the *actual* field-multiplication count Poseidon2 reduces, unlike the SNARK constraint system.
  A thesis chapter on "SNARK-friendly hash choice" should draw exactly this distinction: the metric
  that matters (constraints vs. native operations) depends entirely on where in the stack the hash
  runs, not just which arithmetization the SNARK uses.
- **Plonkish/AIR-based systems** (where gate cost tracks native operation count more directly than
  R1CS's linear-substitution model does) are the setting where this experiment's premise — "cheaper
  linear layer -> cheaper circuit" — would likely hold; a STARK-based redesign of Veil's transfer
  circuit (queue item #9, Nova/Halo2/PLONK) would need this re-measured from scratch under that
  arithmetization, not assumed from this result.

## Open questions (queue candidates for tomorrow)

1. **Validated Poseidon2 migration is now de-prioritized**, not because it's infeasible but because
   its original motivation (proving-time reduction) doesn't hold under measurement. If it's picked
   up again, it should be for a different reason (e.g. moving to a Plonkish system where the
   linear-layer savings would actually show up) and would still need the same official-parameters
   blocker resolved (`MystenLabs`-style GitHub-scope or `sage` toolchain access for
   `HorizenLabs/poseidon2`'s reference constants).
2. **New, better-scoped candidate**: measure native (non-circuit) Poseidon vs. a properly-sourced
   Poseidon2 hashing throughput for the indexer/Merkle-tree-building path
   (`scripts/src/compliance-utils.ts`) — this is where the linear-layer efficiency this experiment
   ruled out for proving time would actually show up as a real number Veil pays (indexer throughput,
   queue item #4's batch-insertion cost).
3. On-chain gas measurement (queue item #1) needs either the sandbox's network policy to allow
   `fullnode.testnet.sui.io`, or this session's GitHub scope to include `MystenLabs/sui` for a
   release-binary download — both are configuration outside what a retry within this session can
   fix. Recommend requesting one of these explicitly before the next run reaches this item again.
4. Does circom's `--O2` (full non-linear simplification, not the `--O1` default used here and by
   `compile.sh`) change this result? Unlikely to matter for a pure linear-layer question (O1 already
   handles linear substitution; O2 adds non-linear/Gaussian-elimination-style simplification), but
   untested — cheap to check if it comes up again.
