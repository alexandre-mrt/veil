# 2026-07-19 — Baseline measurement

## Hypothesis

Veil's own circuit, proving, and test numbers can be measured directly, in one run, on one
machine, without relying on any figure that was only ever estimated or copied forward — and doing
so will surface at least one place where the aspirational infrastructure this nightly loop assumes
(a `CLAUDE.md`, `.claude/skills/veil-*`, `docs/research/`) doesn't actually exist yet.

Falsifiable form: **every number in README.md's "Real constraint counts" and "Test counts" tables
can be independently reproduced on a fresh machine to the exact digit, and at least one axis of the
originally-scoped baseline (constraints, proving time, proof/VK size, on-chain gas, browser proving
latency) will turn out to be unmeasurable in this sandbox for a documentable, non-arbitrary reason.**

Both halves held. See Results.

## Threat / privacy model

A baseline measurement isn't a privacy or soundness change — no circuit constraint moved, no
verifier logic changed, no new adversary capability is introduced or removed. This section is
short because the honest answer is "not applicable to most of STRIDE," and saying so explicitly is
more useful than padding it out.

**What this experiment touches:** none of Veil's cryptographic assumptions. The BN254 discrete-log
hardness Groth16 soundness rests on (`docs/threat-model.md` S2), the trusted-setup honest-majority
assumption, ECDH P-256 auditor confidentiality (I5), and every existing STRIDE mitigation are
unchanged. No circuit file, Move source file, or verification key was edited.

**What a chain observer / malicious prover / auditor could newly learn from this PR:** nothing.
The artifacts this PR adds (`scripts/bench/*`, `docs/research/*`, `BASELINE.md`) are development
tooling and documentation; none of them touch what gets deployed, what gets emitted on-chain, or
what proof format is accepted. The one arguably-relevant fact this PR *publishes* that wasn't
public before: exact proving latency and circuit-size numbers, which is exactly the kind of
information a rational attacker (or a rational integrator) already assumes is measurable by running
the same open-source circuits themselves. Publishing it doesn't create a new capability.

**Residual surface:** unchanged from `docs/threat-model.md`. In particular, none of the accepted
risks (E6 Sybil, E3 UpgradeCap, I4 deposit-linkability) are affected by this experiment.

**Assumptions:** the trusted setup used here (`circuits/scripts/compile.sh`'s single-contributor
dev ceremony, run fresh in this sandbox) is explicitly non-production, exactly as already documented
in README.md "Known blockers" #1. This PR does not run or reference the multi-party ceremony script.

**STRIDE mapping:** none — no threat-model row changes as a result of this experiment.

## Approach

### What I built

1. **`scripts/bench/prove-latency.mjs`** — a reusable Node benchmark that builds real,
   circuit-satisfying witnesses for `transfer.circom`, `compliance.circom`, and `withdraw.circom`
   (witness construction mirrors `circuits/test/*.test.mjs`'s `buildValidWitness` exactly — same
   domain tags, same Merkle-path convention — so the benchmark proves and verifies genuine witnesses,
   not placeholders), runs `snarkjs.groth16.fullProve` + `.verify` N times per circuit, and reports
   mean/min/max prove time, verify time, and artifact sizes. Writes `scripts/bench/results-latest.json`.

2. **`scripts/bench/browser-prove.mjs` + `scripts/bench/browser-harness/`** — the same measurement,
   but inside real headless Chromium (Playwright driving the pre-installed browser at
   `/opt/pw-browsers/chromium-1194`) using `snarkjs.min.js`, the actual UMD build the frontend's
   `useProofGeneration.ts` would load via `dynamicRequire("snarkjs")`. This answers "what does a
   user's browser actually pay for the WASM proving frontend code claims to do" rather than
   inferring it from Node timing, which turned out to matter (see Results — the two are not
   interchangeable).

### What I rejected before building it

- **Copying the browser number from documentation instead of measuring it.** README claims
  "snarkjs proving in a Web Worker" for the frontend; a `grep` for `new Worker(` in
  `frontend/src` found none — `useProofGeneration.ts` runs proof generation on the main thread via
  dynamic import. I measured what the code actually does (main-thread Chromium proving), not what a
  comment claims it does, and note the discrepancy here rather than silently "fixing" the README
  wording, which is out of scope for a measurement-only PR.
- **Driving the real Next.js UI end-to-end (wallet connect, on-chain calls) for the browser bench.**
  Considered and rejected: it would require mocking `@mysten/dapp-kit`, a Sui wallet, and on-chain
  state, none of which the browser proving *latency* number depends on. A minimal static HTML
  harness that calls the exact same `snarkjs.groth16.fullProve` with the exact same `.wasm`/`.zkey`
  isolates the number being measured (WASM proving cost) from everything else in the app.
- **Estimating on-chain gas from `sui move test` gas-metering output.** `sui move test` does not
  report gas by default, and — moot in this sandbox anyway — reaching it requires the `sui` CLI
  binary and (per `contracts/Move.toml`) a `git` dependency fetch from `github.com/MystenLabs/sui`.
  Neither is possible here (see BLOCKED). I considered inferring gas from the deployed testnet
  package's historical transactions via the fullnode JSON-RPC endpoint instead of the CLI — also
  blocked, same egress policy, documented below rather than worked around.
- **Building `circom` from source via `cargo install` or `git clone`.** `crates.io` doesn't carry a
  real `circom` package (only unrelated crate names), and `github.com/iden3/circom` is unreachable
  under this sandbox's egress policy. Used `@distributedlab/circom2` (an npm-distributed WASM build
  of circom 2.2.2) instead — a real compiler, not a mock, verified by cross-checking its constraint
  counts against README's already-published numbers (exact match).

### A toolchain finding worth recording

`@distributedlab/circom2`'s WASM `--wasm` codegen was flaky in this sandbox: three separate
compile attempts either segfaulted mid-write or silently produced a truncated `.wat`/`.r1cs` file
that `snarkjs r1cs info` then reported as corrupt (`Missing section 1`). Retrying the exact same
command 2–5 times always eventually succeeded with a complete, valid file — this looks like a
resource/timing race in the WASI runtime under Node, not a determinism bug in the compiler itself
(re-running produced byte-stable constraint counts every time it *did* succeed). Anyone re-running
this benchmark should wrap circom2 invocations in a "retry until the r1cs file round-trips through
`snarkjs r1cs info`" loop, exactly like `circuits/build-circuit.sh` (added in this PR) does. Also:
circom2's generated `.wat` uses pre-finalization WebAssembly opcode names (`get_local` instead of
`local.get`, `i32.wrap/i64` instead of `i32.wrap_i64`) that `wabt`'s current parser rejects —
`circuits/wat2wasm.mjs` (added in this PR) does the mechanical rename before compiling to `.wasm`.

```
  "userAgent": "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) HeadlessChrome/141.0.0.0 Safari/537.36"

```

Browser proving (1310.8ms mean) is **~1.4x slower** than Node proving of the identical witness
against the identical `.wasm`/`.zkey` (905.0ms mean) on this machine. This is a real, measured
engine-overhead effect — not a difference in circuit or input. Note on variance: two earlier 5-run
invocations of the same harness returned means of 1852.8ms and 1349.7ms — a ~40% swing between two
back-to-back invocations on this shared sandbox VM. The 10-run number is more trustworthy than
either 5-run sample; anyone using this harness for a real comparison should run ≥10 iterations and
report the range, not a single small-N mean.

### BLOCKED

**On-chain gas per entry point, and the Move contract test suite (`sui move test`).**

- The `sui` CLI is not installable here: it is not published on crates.io under a real package
  (`cargo install sui` resolves to an unrelated 0.0.1 name-squat with zero dependencies — not the
  Sui blockchain CLI), and its actual source, `github.com/MystenLabs/sui`, returns `403` on
  `CONNECT` through this sandbox's egress proxy (org policy — "do not retry or route around it,"
  per the proxy's own operating instructions).
- Bypassing the CLI by querying the already-deployed testnet package directly over JSON-RPC
  (`fullnode.testnet.sui.io:443`) was also attempted and also returned `403` on `CONNECT` — same
  policy, different host.
- Independent of both of the above: `contracts/Move.toml` declares
  `Sui = { git = "https://github.com/MystenLabs/sui.git", ... }`, so even a hypothetical local `sui`
  binary would still need to fetch the framework dependency from a blocked host to run `sui move
  test` at all.

No number is reported for either. `BASELINE.md` records this as BLOCKED, not as an estimate.

## Verdict: **KEEP (partial)**

Merged. `BASELINE.md` created and reflects everything measured this run. The partial qualifier is
load-bearing: on-chain gas per entry point and the Move test suite are explicitly BLOCKED, not
silently omitted, and browser proving latency covers `transfer.circom` only. Queue item #1 is
**settled as far as this sandbox's network egress policy allows** — re-open it (or add a follow-up
item) the day `sui` CLI or an allow-listed Sui RPC endpoint becomes reachable from wherever this
loop runs.

## Where this could be used

- **Any Circom + snarkjs project bootstrapping CI in a network-restricted sandbox** — the
  `@distributedlab/circom2` WASM-compiler fallback and the retry-until-valid pattern in
  `circuits/build-circuit.sh` apply to any project whose CI runner can't reach GitHub or build the
  native Rust `circom` toolchain (common in locked-down enterprise CI, air-gapped research
  clusters, or classroom/thesis environments without a full dev-toolchain image).
- **Any team evaluating client-side ZK proving UX** (wallets, browser extensions, mobile-web
  dApps) — `scripts/bench/browser-prove.mjs` is a reusable pattern for "what does the actual
  browser engine cost, not the Node estimate" that generalizes past Veil: point it at any
  `snarkjs`-based circuit and it reports the real number, with the variance caveat this run
  surfaced (small-N single-invocation samples on shared/cloud CI hardware are unreliable — use ≥10
  runs).
- **A specific thesis chapter**: "measuring the proving-latency gap between server-side/CI proof
  generation and client-side WASM proving for regulatory-threshold ZK compliance proofs" — this
  run's ~1.4x (and, in the noisier samples, up to ~2x) browser-vs-Node gap for a ~13.6k-constraint
  circuit is a concrete anchor point for arguing whether a given deployment (e.g. "confidential
  payroll on Sui with a t-of-n auditor board", queue item #4) needs a lighter circuit, a
  server-assisted proving flow, or can live with in-browser proving as-is.

## Open questions

1. Would the browser-vs-Node proving gap grow or shrink for `compliance.circom` and
   `withdraw.circom`? The harness only covers `transfer.circom`; extending it to the other two is
   mechanical (same pattern, different witness builder) — good first task for whoever picks up
   queue item #1's follow-up, or folds naturally into whichever circuit-change experiment runs next.
2. Is the `circom2` WASM segfault/truncation actually a resource race (memory pressure, WASI file
   sync), or something specific to this sandbox's cgroup/container setup? Worth a `strace`/`dmesg`
   pass if it starts blocking a night's experiment instead of just costing a few retries.
3. What does on-chain gas per entry point actually look like? This is now the natural next
   BLOCKED-item to re-attempt the moment `sui` CLI or a reachable Sui RPC endpoint exists in
   whatever environment runs this loop next — see `EXPERIMENTS.md` item re-ranked to reflect this.
4. Given prover time (transfer.circom, ~900ms server-side) is one of the two numbers this baseline
   pins down concretely, batched/aggregated proofs (queue item #1, promoted) is the most direct
   next lever — re-verify against this baseline once built, not against README's older claims.
